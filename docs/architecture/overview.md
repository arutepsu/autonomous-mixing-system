# Architecture

## Confirmed decisions
- Offline Python processing of synchronized WAV stems; modular monolith with a CLI; no DAW plugin in M0 ([ADR-001](../decisions/0001-offline-python-workflow.md)).
- Deterministic audio analysis and DSP; Claude proposes structured actions but never performs measurements or audio processing ([ADR-001](../decisions/0001-offline-python-workflow.md)).
- Single agent with deterministic orchestration: application code controls the loop, validates proposals, executes DSP and verifies results ([ADR-004](../decisions/0004-single-agent-deterministic-orchestration.md)).
- uv-managed environment, Python 3.11 ([ADR-002](../decisions/0002-uv-dependency-management.md)).
- Track-role-agnostic design: stems carry declared roles; components must not assume specific instruments such as kick/bass. Problem-specific components are added only in their roadmap phase; analysis parameters and thresholds must be configurable and documented ([ADR-006](../decisions/0006-research-first-development-policy.md)).

## Target pipeline (planned)
Audio I/O -> deterministic features -> detectors -> structured problem candidates -> Claude proposal (`decision_agent`) -> action validator -> DSP execution -> verification -> accept/revert -> experiment report.

Structure ([ADR-027](../decisions/0027-hexagonal-control-loop-architecture.md), Accepted 2026-11-03; implemented by migration steps M0–M5, completed 2026-11-04, M6 skipped): a hexagonal modular monolith whose `core` will run this pipeline as a MAPE-K-style control loop over immutable records, with DSP analysis, rendering and the Claude `decision_agent` as adapters behind `core.ports`, and `evaluation` reachable only from the experiment runner. The control loop itself does not exist yet. Layout, import and immutability rules: [`engineering-conventions.md`](../project/engineering-conventions.md); migration record and guarantee ledger: [`adr-027-migration-plan.md`](adr-027-migration-plan.md). ADR-027 supersedes ADR-017 and ADR-022.

Hidden-reference boundary ([ADR-010](../decisions/0010-hidden-reference-boundary.md), requirements SR-10): everything up to accept/revert is runtime and never reads the original reference audio or defect-injection ground truth. Run records hold runtime inputs and the action history. Research evaluation joins them with the separately stored hidden evaluation data only after execution.

### Budget gate (`core.loop.budgets`; implemented 2026-11-04, not integrated)
Implements Task 1 of `docs/superpowers/plans/2026-11-04-control-loop-budget-gate-plan.md` (attempt contract, sections 25–26 and 29). `core.records.budgets` adds `BudgetOperation` (decision call, attempt, render call, recovery operation), `BudgetBlockReason` (elapsed time, decision-call, attempt, render-call and recovery-capacity limits), the frozen outcomes `BudgetGrant(operation, usage_after_charge)` and `BudgetBlock(operation, reason, usage)` and the union `BudgetAssessment`; a block rejects a reason unrelated to its operation. `BudgetLimits` and `BudgetUsage` are unchanged. `check_budget(operation, *, limits, usage, elapsed_seconds)` takes a caller-supplied elapsed checkpoint (finite, non-negative, not earlier than recorded usage, else `ValueError`) and returns, in this order: an elapsed-time block at or above the limit; a block when the operation's own count has reached its limit (count limits are inclusive); for a render, a recovery-capacity block when no recovery slot is unused; otherwise a grant whose usage increments only that operation's counter. Recovery is not blocked by exhausted decision, attempt or render counters. Recorded overruns are kept, not clamped; integer counts stay exact. Evidence: `tests/unit/test_loop_budgets.py`.

Limits: a grant is a proposed charge, not authorization, a reservation or proof of dispatch. Nothing charges live counters, reads a clock, reserves recovery capacity, dispatches, retries or records events; the decision retry policy, dispatch-intent journal, post-acknowledgement time/cancellation recheck, deadline interruption and terminal reasons are not implemented. There is still no runnable control loop, and QR-04/OP-04 are not met by this gate alone.

### Diagnosis records (`core.records.diagnosis`; implemented 2026-11-04, not integrated)
Implements Task 1 of `docs/superpowers/plans/2026-11-04-control-loop-diagnosis-records-plan.md` (attempt contract, section 12). New identifiers `ProblemCandidateId` and `DiagnosisCoverageId` (`core.records.identifiers`). `core.records.diagnosis` adds the labels `ProblemFamily` (masking, frequency buildup, phase interaction), `UncertaintyRepresentation` (qualitative, uncalibrated; no calibrated member and no numeric probability field) and `DiagnosisCoverageStatus` (assessed, unavailable, incomplete), and the frozen records `DiagnosticEvidence` (free-text strength and uncertainty, a separate boolean insufficiency flag that requires at least one stated missing item, limitations), `DiagnosisCoverage` (one family, scope and method per row; a method is required unless the row is UNAVAILABLE), `ProblemCandidate` (bound to one coverage row; affected tracks are its scope's tracks; nonempty cited observation IDs) and `DiagnosisReport`. Report construction rejects duplicate coverage IDs, duplicate (family, scope, method) keys and duplicate candidate IDs, and requires every candidate to match the report's project and revision, name an existing row with the same family and method, lie within the row's scope (exact containment; a restricted band requires a contained band), never sit under UNAVAILABLE coverage and be marked insufficient under INCOMPLETE coverage. An empty candidate tuple keeps the meaning of its rows: ASSESSED-empty is not an all-clear and is distinct from UNAVAILABLE or INCOMPLETE.

`validate_diagnosis_references(report, *, state, scope, observations)` requires the report to describe the selected state, every coverage scope to lie within the supplied run scope and known tracks only, unique and correctly typed observations (extras included, otherwise ignored), every cited observation to be supplied and its sources to be current checkpoint members via `validate_observation_sources` (a retained member produced at an older revision is valid; a superseded artifact is not), and a candidate whose cited results are all `Unavailable` to be marked insufficient. Evidence: `tests/unit/test_diagnosis_records.py`.

Limits: these are descriptive contracts and structural/provenance checks only. No detector, DSP method, threshold, calibrated confidence, action gate, `core.diagnosis` package or `Situation` field exists; the records do not show that any method ran or that a candidate is perceptually real. D11 (uncertainty schema and methods) remains open, and FR-05/FR-06 are not met.

### Action capability view (`core.records.capabilities`, `core.admission.capabilities`; implemented 2026-11-04, not integrated)
Implements Task 1 of `docs/superpowers/plans/2026-11-04-control-loop-action-capabilities-plan.md` (attempt contract, sections 11, 14 and 28). `core.records.capabilities` (imports only `identifiers`, `invariants`, `observation`, never admission, decision or run records, so a later `Situation` can carry the view without a records cycle) adds the frozen records `GainBounds(minimum_db, maximum_db)` (inclusive absolute additional gain in dB, finite, minimum <= maximum, values kept exactly), `RendererCapabilities(reference, gain_bounds)` (explicit, versioned renderer support; `None` declares no gain support), `AvailableTrackGain(track_id, bounds)` (a potential `SetTrackGain` target, not an action) and `ActionCapabilityView` (project, revision, context identity/version, policy and renderer references, scope and unique in-scope gain actions). `build_action_capability_view(*, state, scope, context, policy, renderer)` first validates scope and context against the snapshot, the policy project and every policy permission's track (also outside the scope and without renderer gain support), then walks `scope.track_ids` in order and omits protected tracks, tracks without an explicit permission, all tracks when the renderer declares no gain support, and tracks whose permission and renderer ranges are disjoint; otherwise it advertises the exact intersection (equal endpoints allowed; no clamping, rounding or default bounds). Only gain is representable; no EQ, dynamics or stereo action is advertised. Evidence: `tests/unit/test_action_capabilities.py`.

Limits: the view describes declared availability; it is not execution permission, a justified proposal or proof that rendering is safe, and an empty view does not mean the mix has no problem or that No Change is justified. `admit_action` still checks only producer protections and `ActionAdmissionPolicy` bounds: it does not yet enforce the renderer descriptor or the advertised scope, and no driver yet supplies a renderer descriptor matched to the configured renderer. The view is not part of `Situation`; actual gain bounds remain a D5/configuration decision. FR-07, FR-08 and FR-11 are not met by this view.

## Implemented (M0)
M0 implements only Audio I/O -> features -> descriptive JSON report. Do not claim masking detection from overlap measures alone.

| Module | Responsibility |
| --- | --- |
| `autonomous_mixing.adapters.dsp_analysis.io` | Load WAV stems as float64 `(frames, channels)`; reject non-WAV, unreadable, too-short (< 2048 frames), > 2-channel and non-finite input; require equal sample rate and frame count for a pair. |
| `autonomous_mixing.adapters.dsp_analysis.features` | Mono fold-down, RMS/peak dBFS, STFT magnitudes, band-power and temporal-coactivity proxies. |
| `autonomous_mixing.adapters.dsp_analysis.analysis` | `analyze_pair`: combines the above into the `m0.1` report dict, including input SHA-256 hashes. |
| `autonomous_mixing.drivers.cli` | `autonomous-mixing analyze`: writes the JSON report; validation errors exit with code 2 and a one-line message. *(2026-11-03: also rejects a report destination that refers to either input; see "Report destination guard" below.)* |
| `scripts/generate_test_audio.py` | Deterministic synthetic kick/bass stems, formerly used for manual smoke runs (not perceptual ground truth). No test depends on it; under review per ADR-006. |

Analysis parameters (STFT 2048/512, 30–200 Hz band, 10 % coactivity threshold) are fixed in code. `configs/analysis.yaml` documents them as a proposed manifest but is **not read** by the code yet.

**Known deviations from ADR-006 (M0):** the two inputs are named `kick`/`bass` in the CLI, `analyze_pair` and the report keys, and the parameters above are hardcoded. Retained unchanged until reviewed; do not extend this pattern.

**Report destination guard (2026-11-03, bounded defect correction; no ADR).** Before this correction the CLI wrote the report to `--output` without comparing it with the inputs, so a destination naming an input stem replaced that source file with the JSON report. This is corrected; no requirement status changed and QR-01 remains untested as recorded in the requirements.
- `drivers.cli._report_conflict` compares filesystem identity: `os.stat` (following symbolic links) of the destination and of each input, then `os.path.samestat`. No path strings are compared. Direct paths and relative/absolute, symbolic-link and hard-link aliases of either input are therefore rejected where the platform supports them.
- Order: analysis and input validation run first, so their errors are reported unchanged. The check then runs before the parent directory is created and again after it, immediately before writing; the second check covers paths such as `missing/../input.wav`, which on POSIX resolve to an input only once `missing` exists.
- Rejection exits with code 2 and a one-line `error: …` message on stderr, with no traceback and no `Wrote …` line; the input bytes are preserved.
- A nonexistent destination is allowed. Any other `OSError` while inspecting an existing destination or an input rejects with `error: cannot verify …` and nothing is written.
- New reports and replacement of an unrelated existing report still work. Arguments, the `m0.1` report schema and extension handling (any extension is accepted) are unchanged.
- Destinations whose parent component is an existing file: on POSIX the destination `stat` is expected to fail with a non-`FileNotFoundError` error, so the CLI now reports `error: cannot verify …` with exit 2 instead of a traceback (implementer-stated; not exercised on native POSIX). On Windows 11 a documentation probe (2026-11-03, one-off, not regression coverage) observed that `os.stat` reports `FileNotFoundError` for such a path, the first check allows it, and parent creation then raises an uncaught `FileExistsError` (traceback), as before the correction. The source files are not written in this case. *(Superseded 2026-11-03, follow-up correction: the Windows traceback described here is resolved; see the next bullet.)*
- Report-parent creation failures (2026-11-03 follow-up): the order is still check, parent creation, check, write, and both identity checks remain. Only the parent-directory creation (`path.parent.mkdir(parents=True, exist_ok=True)`) is wrapped. If it raises `FileExistsError`, `NotADirectoryError`, `PermissionError` or `FileNotFoundError`, the CLI prints `error: cannot create report directory <parent>: <exc>` on stderr and exits with code 2. No report is written and no `Wrote …` line is printed; inputs and blocking files are left unchanged. On Windows this now covers an existing file (including an input WAV) as the direct or a nested parent component. On POSIX the identity check is expected to reject these cases first with `error: cannot verify …`; this is untested. Not covered: other (unexpected) errors from parent creation still propagate unchanged, and errors while writing the report are not handled by this change; not every CLI filesystem error is handled. Parent directories created before a failure are not cleaned up. No locking or race-free guarantee is added.
- Follow-up evidence (kept by source):

  - Independent focused review: 25 CLI tests passed; 2 hard-link skips were caused by sandbox permissions.
  - Independent scoped lint, formatting and CLI help passed.
  - No independent full-suite rerun for this small follow-up.
  - Native Windows file-as-parent cases passed; there was no native POSIX run.
  - uv was unavailable; dependency files are unchanged.
  - No real `PermissionError` from parent creation was produced; that type is covered only by an injected test.
- Limits: a pre-write check, not a lock; there is no race-free protection between the check and the write. Parent directories created before a second-check rejection are left in place. Identity checks were exercised on Windows 11 NTFS only. This guard concerns the M0 report output; it does not address F4, which concerns the future file adapter and execution service.
- Evidence (kept by source):
  - Implementer full run: 2,791 passed, 3 skips.
  - Independent full run: 2,777 passed, 17 platform/sandbox skips.
  - Both original source-overwrite audit probes now pass.

### Numerical kernels (`dsp`)
`autonomous_mixing.adapters.rendering.dsp` implements the numerical rules of `ProcessingSpec` (ADR-021: FLOAT64, DB_AMPLITUDE, RECIPE_SEQUENTIAL, PRESERVE) on in-memory NumPy arrays; the container and sample-encoding settings belong to the future file adapter. *(2026-11-03: the container and sample-encoding mapping is now implemented at the WAV writer boundary only, `adapters.rendering.wav_output`, below; the kernels are unchanged and nothing connects them to the writer.)* Neither the domain nor the application imports the package. Evidence: `tests/unit/test_audio_dsp.py` (126 test cases passed; full suite 1,218 passed; ruff lint and scoped formatting passed; independent review, 2026-10-22). Status: implemented for the in-memory kernels only; they contribute to FR-08, FR-17, QR-01 and QR-02 but complete none of them.

| Function | Numerical rule |
| --- | --- |
| `apply_absolute_gain(input_samples, gain_db)` | `gain_db` must be exactly a built-in `int` or `float` (`bool`, NumPy scalars including `np.float64`, and `int`/`float` subclasses are rejected before any conversion or arithmetic). Factor `10 ** (gain_db / 20)` in built-in arithmetic must be finite and strictly positive: overflow or rounding to zero is rejected even for silent input; positive subnormal factors are allowed. Multiplies the fixed input; a non-finite product is rejected. Repeated calls on the same input do not compound. |
| `sum_stems(stems)` | Nonempty exact `tuple` of identically shaped arrays. A new float64 zero accumulator receives each stem in tuple order, with a finiteness check after every addition. No reordering, stacked or compensated summation, normalization, clipping or limiting. |
| Shared input and output rules | Inputs must be exact `np.ndarray`, native-endian float64, 2-D `(frames, channels)`, at least one frame, one or two channels, finite. Read-only, non-contiguous and negative-stride views are accepted. No cast, reshape, broadcast, padding or fold-down; finite values outside [-1, 1] are preserved. Inputs are never mutated, also on failure; outputs are newly allocated. Floating-point conditions are handled under a local `np.errstate`, and the caller's NumPy error settings are restored. Expected failures raise `ValueError`. |

Limits: no WAV processing adapter, execution service or connected correction pipeline exists, and only tests call the kernels. Array immutability does not establish source-file protection (QR-01); F2 and F4 remain open (see Open questions). A fixed operation order does not promise bitwise-identical results across platforms, and no cross-platform identity is claimed. The tests use synthetic numerical arrays; no perceptual or research-performance result follows from them. No test yet enforces the infrastructure package's own import boundary. *Superseded (2026-10-22, ADR-022): source-import rules for the existing infrastructure modules are now enforced; see Import boundaries below.*

### Read-only WAV integrity checks (`integrity`, formerly `verification`)
`check_wav_integrity(artifact, *, max_file_bytes, max_decoded_bytes) -> CheckedAudio` checks one existing file against its `AudioArtifact` metadata. It writes, renames and removes nothing. It imports the `core.records` interface (`AudioArtifact`) and soundfile/libsndfile. Evidence: `tests/unit/test_audio_verification.py` (87 test cases passed, no skips; full suite 1,305 passed; ruff lint and scoped formatting passed; independent review, 2026-10-22). Status: implemented for read-only verification of a single artifact. It contributes to QR-01, QR-02, QR-03, FR-02 and FR-17 but completes none of them; requirement statuses are unchanged.

| Element | Behaviour |
| --- | --- |
| Arguments | `artifact` must be an `AudioArtifact`; both limits must be positive built-in `int`s, with no default and no scientific meaning. Invalid arguments raise plain `ValueError` before any file access. |
| Path | `artifact.location` must be an absolute local path. Relative, URI-style and UNC/network/device-namespace forms (and NUL characters) are rejected lexically as `UNSUPPORTED_PATH`. |
| Capture | Regular-file check on the pathname, one `open`, regular-file check on the opened handle, then a bounded read of at most `max_file_bytes + 1` bytes. Reads are chunked at no more than 1 MiB each (an I/O buffer size, not a scientific threshold), so arbitrarily large positive limits are accepted while the total-read bound is kept. A larger payload is rejected (`RESOURCE_LIMIT`). |
| Hash | The SHA-256 of the captured payload must equal `artifact.content_hash` before any decoding (`HASH_MISMATCH`). |
| Decode | From the same captured bytes in memory; the path is not opened a second time. The container is detected from content, not the file extension, and must be libsndfile `WAV`, `WAVEX` or `RF64`. Declared sample rate, channel count and frame count must match (`METADATA_MISMATCH`). The file needs at least one frame and one or two channels. Decoded storage (frames × channels × 8 bytes) is checked against `max_decoded_bytes` before decoding. Fewer decoded frames than inspected, or unreadable content, give `INVALID_WAV`. Samples must be finite (`NONFINITE_SAMPLES`). |
| Result | `CheckedAudio(artifact, samples, container, subtype, verified_sha256)`: frozen, with identity equality. `samples` is a native float64 `(frames, channels)` array returned read-only, without normalization, clipping, resampling, padding or fold-down. `container` and `subtype` are libsndfile's names for the detected format. |
| Failures | Expected file and content failures raise `IntegrityError`, a `ValueError` subclass whose `.code` is a `IntegrityFailureCode`: `UNSUPPORTED_PATH`, `NOT_FOUND`, `NOT_READABLE`, `NOT_REGULAR_FILE`, `RESOURCE_LIMIT`, `HASH_MISMATCH`, `INVALID_WAV`, `METADATA_MISMATCH`, `NONFINITE_SAMPLES`. |

Limits:
- Verification establishes the identity of the captured payload only. It does not establish that the pathname still holds those bytes afterwards; a future processor must consume the returned samples or reverify whatever it reads later.
- `check_wav_integrity` has no directory confinement and no protection against aliases, symbolic links, junctions or other reparse points. Neither entry point provides race-free capture. (2026-11-02: `check_resolved_wav_integrity` adds canonical root containment at resolution time only; see below.)
- The byte limits bound the captured payload and the returned sample storage only. They do not bound total process or decoder memory.
- The read-only array flag guards against accidental mutation; it is not a security boundary.
- Existing records and fixtures use relative locations such as `outputs/{id}.wav`, which `check_wav_integrity` rejects. *Superseded (2026-11-02): such locations can now be verified through `resolve_artifact_location` and `check_resolved_wav_integrity` with an explicit root (see below); `check_wav_integrity` itself still rejects them.*
- No workspace allocator, WAV writer, processing adapter or connected execution pipeline exists yet. F4 (write protection, workspace confinement) and F2 (acceptance/validation evidence linked to the candidate state) remain open. *(2026-11-02: the "no workspace allocator" part is superseded by `adapters.rendering.workspaces`; the rest still holds.)* *(2026-11-03: the "no WAV writer" part is superseded by `adapters.rendering.wav_output`; there is still no processing adapter or connected execution pipeline, and F4 and F2 remain open.)*
- No perceptual or research-performance result is established.
- Platform: tested on Windows. soundfile 0.14.0 is the version pinned in `uv.lock`; libsndfile 1.2.2 is taken from the implementation report and is not recorded in the lockfile. The POSIX-specific `IsADirectoryError` branch was not exercised on a real filesystem. Permission failures and a non-regular opened handle were exercised only via test doubles.

### Read-only artifact-location resolution (`locations`, formerly `filesystem`; ADR-023, Proposed)
`autonomous_mixing.adapters.rendering.locations` (implementation module `locations`) owns local interpretation of artifact locations. It exports exactly four names:
- `ResolvedArtifactLocation(artifact, configured_root, resolved_root, absolute_path)`;
- `LocationResolutionFailureCode`, with seven codes: `UNSUPPORTED_PATH`, `INVALID_ROOT`, `NOT_FOUND`, `NOT_READABLE`, `OUTSIDE_ROOT`, `RESOLUTION_LOOP`, `STALE_RESOLUTION`;
- `LocationResolutionError`, a `ValueError` subclass with `.code` and a message prefixed by the code value;
- `resolve_artifact_location(artifact, *, root)`.

The resolver inspects filesystem metadata only. It opens no file content and writes, creates, renames or removes nothing.

Evidence:
- Tests: `tests/unit/test_artifact_locations.py`, `tests/unit/test_resolved_audio_verification.py` and the extended `tests/unit/test_application_infrastructure_boundaries.py` (retired in ADR-027 step M4; rules now in `tests/architecture/`) and `tests/unit/test_application_component_compatibility.py` (retired in ADR-027 step M4; rules now in `tests/architecture/`).
- Implementer rerun: full suite 1,870 passed, 1 skipped (the POSIX-only permission test).
- Independent review: 1,866 passed, 5 skipped, because four Windows junction tests could not run under the review environment's sandbox permissions. Ruff lint, scoped formatting and CLI help passed.

Status: implemented as read-only resolution and verification. It contributes to existing artifact-verification and provenance requirements but completes none of them; requirement statuses are unchanged.

| Element | Behaviour (as implemented) |
| --- | --- |
| Record | `ResolvedArtifactLocation` is a frozen dataclass. `artifact` is the original `AudioArtifact` object: its location stays as written, including relative, and no field is changed or copied. `configured_root` is the caller's root string verbatim. `resolved_root` and `absolute_path` are strings produced by strict resolution. Construction checks types and non-blank strings only, without filesystem access. A record therefore certifies neither existence nor canonicality, may be stale, and is not an authorization, capability or security token. |
| Arguments | `artifact` must be an `AudioArtifact` and `root` a non-blank `str` (a `Path` is rejected); otherwise plain `ValueError` is raised before filesystem access. There is no default root, root registry, current-directory fallback, URI decoding, environment-variable or tilde expansion, or foreign-platform translation. |
| Lexical policy (native platform only; first the root, then the location) | Raises `UNSUPPORTED_PATH` for: NUL characters; two leading separators of either kind (treated as UNC/network/device on every platform); URI-style prefixes (the verifier's pattern, two or more scheme characters followed by `:`); any `..` component. The root must be fully absolute. On Windows it also rejects drive-relative and root-relative forms, and it intentionally rejects colons outside the drive prefix, including alternate data streams. On POSIX it also rejects Windows drive syntax. The URI-style, Windows-drive and two-leading-separator exclusions are intentional supported-input restrictions applied on all platforms. Valid POSIX names such as `take:1.wav`, `a:b.wav` or `//`-prefixed paths are therefore outside the supported input form; they are not invalid POSIX names. `.` components are allowed. |
| Resolution | The root is resolved strictly and must be an existing directory; a root reached through a link is allowed, and `resolved_root` records the actual directory. Relative locations are joined to the resolved root; absolute locations are used directly. The candidate is resolved strictly and must exist. A directory candidate can resolve, and the verifier rejects it later. |
| Containment | Exact path-component comparison (component prefix, not string prefix) after strict canonical resolution of both root and candidate. A target equal to the root is rejected as `OUTSIDE_ROOT`. Links and junctions whose canonical target lies inside the root are allowed, including an absolute alias outside the root pointing inside it; canonical targets outside the root are rejected. |
| Failures and precedence | Order: argument checks, root lexical check, location lexical check, strict root resolution and directory check, strict candidate resolution, containment; the first failure wins. A missing root or a root that is not a directory gives `INVALID_ROOT`. A missing candidate or intermediate component gives `NOT_FOUND`, even when the text looks outside the root. `PermissionError` gives `NOT_READABLE`. An `ELOOP` `OSError`, or an exception of exact type `RuntimeError` (Python 3.11 pathlib's cycle report), from `Path.resolve` gives `RESOLUTION_LOOP`. Other `OSError`s and other exceptions, including `RuntimeError` subclasses, propagate unchanged. Exceptions are mapped around the individual resolve/stat calls only, not around the whole resolver. |

**Verifier entry point.** `check_resolved_wav_integrity(location, *, max_file_bytes, max_decoded_bytes) -> CheckedAudio` (in `audio.verification`) works in five steps:
1. It validates the record type and both limits before any filesystem access.
2. It resolves `location.artifact` afresh against `location.configured_root`. Resolution errors propagate unchanged as `LocationResolutionError`.
3. It raises `STALE_RESOLUTION` before any content open if the fresh `resolved_root` or `absolute_path` differs from the record's by exact string comparison. A canonically equal but textually different record is therefore stale.
4. It verifies the freshly resolved path through the private capture/hash/decode pipeline it shares with `check_wav_integrity`, against the original artifact's declared hash and metadata.
5. The result's `CheckedAudio.artifact` is the original object, and the resolution record is not retained in it.

After successful resolution, disappearance or permission failure give the existing audio capture codes. Changed bytes at the same path give `HASH_MISMATCH`. Path equality does not prove file identity.

`check_wav_integrity` keeps its API and behavior: absolute paths only, no root confinement. The `adapters.rendering` facade now has seven exports.

Implementation choices recorded as observed in code (not all have a dedicated test):
- Supported-input restrictions, intended and applied on all platforms: the verifier's URI pattern, Windows drive syntax and two leading separators (UNC form) are excluded. Valid POSIX names such as `take:1.wav`, `a:b.wav` or `//`-prefixed paths are outside the supported input form.
- On Windows, colons outside the drive prefix, including alternate data streams, are rejected as intended.
- Containment compares path components exactly after strict canonical resolution. The independent reviewer's native Windows casing probe passed: a differently cased but equivalent path resolved within the root. That was a one-off review probe, not regression coverage; the suite has no dedicated casing test.
- The stale check compares exact strings.
- The Windows `..` check matches exact components only (forms such as `.. ` or `...` are not lexical traversal), and canonical containment is the backstop.
- Only an exact `RuntimeError` maps to `RESOLUTION_LOOP`.

Limits:
- Strict resolution and containment describe the filesystem as observed during the calls. They give no race-free confinement, link immutability, hard-link uniqueness, exclusive access, write protection or source protection.
- There is no workspace allocation, WAV writing, processing adapter or connected execution pipeline. *(2026-11-02, later: the "no workspace allocation" part is superseded by `adapters.rendering.workspaces`, below; the rest still holds.)* *(2026-11-03: the "no WAV writing" part is superseded by `adapters.rendering.wav_output`, below; no processing adapter or connected execution pipeline exists.)*
- F4 and F2 remain open.
- No perceptual or research-performance result follows.
- Platform evidence (implementer, Windows 11 with Developer Mode) covers real file and directory symlinks and junctions: inside→inside is allowed, inside→outside is rejected, root aliases resolve, and real symlink and junction cycles are detected. Permission failures, the `ELOOP` branch and propagation of unexpected errors were exercised only through test doubles, so they are not real-platform evidence. The real POSIX permission test was skipped on Windows.

### Output workspace allocation (`workspaces`, formerly `workspaces.allocation`; ADR-024, Proposed)
`autonomous_mixing.adapters.rendering.workspaces` (implementation module `allocation`) turns an application-issued `ExecutionWorkspace` into one fresh, empty directory below an explicit output root. It is a separate component from the read-only `filesystem` resolver. It creates exactly one directory and writes no audio, markers or manifests. It never creates the root or parents, and never deletes, renames, reuses or cleans up anything.

The component exports exactly six names (*superseded 2026-11-03: seven, because `validate_allocated_workspace` from the new `validation` module was added; see "Workspace revalidation" below. The six allocation names and their identities are unchanged.*):
- `WorkspaceRoot(root_key, path)`;
- `WorkspaceAllocationRequest(workspace, root, state, protected_locations)`;
- `AllocatedWorkspace(request, resolved_root, directory)`;
- `WorkspaceAllocationFailureCode`, with nine codes: `ROOT_KEY_MISMATCH`, `INVALID_INVENTORY`, `INVALID_ROOT`, `UNSUPPORTED_PATH`, `PROTECTED_LOCATION`, `PROTECTED_OVERLAP`, `COLLISION`, `NOT_WRITABLE`, `WORKSPACE_CHANGED`;
- `WorkspaceAllocationError(code, message, *, created_directory=None)`, a `ValueError` subclass with a code-prefixed message;
- `allocate_workspace(request)`.

Evidence: `tests/unit/test_workspace_allocation.py` and the extended `tests/unit/test_application_infrastructure_boundaries.py` (retired in ADR-027 step M4; rules now in `tests/architecture/`). Attributions:
- Coordinator-reported full run: 2,289 passed, 2 platform skips (`tests/unit/test_artifact_locations.py`, "POSIX non-root only"; `tests/unit/test_workspace_allocation.py`, "POSIX hosts impose no Windows device-name restriction").
- Independent correction review: 645 passed, 5 skips, four of which are additional junction skips caused by sandbox restrictions in the review environment. Scoped lint and formatting passed.
- No fresh lockfile check: uv was unavailable in that environment; `pyproject.toml` and `uv.lock` are unchanged.

Status: implemented as directory allocation only. It reduces, but does not close, F4. No requirement is completed and no requirement status changes.

| Element | Behaviour (as implemented) |
| --- | --- |
| Records | Frozen dataclasses. Construction checks types, non-blank text, tuple element types and duplicate protected identity keys `(project_id, artifact_id)` without filesystem access. Duplicate keys are rejected even with equal metadata; distinct keys may share one physical file. An `AllocatedWorkspace` can be built manually or be stale. It is not proof of allocation or ownership, not permission to write, and not a security capability. The original workspace, root, state and artifact objects are retained unchanged. |
| Mandatory protection coverage | The union of `state.audio.artifacts` and every `state.processing.track_gains[].input_artifact`, keyed by identity: current audio members plus fixed input baselines. Each must appear in `protected_locations` with exactly equal metadata, otherwise `INVALID_INVENTORY`. Further history or cross-project entries are caller-supplied and receive the same checks, but nothing proves the supplied set exhaustive. |
| Protected checks | In tuple order, each entry is freshly re-resolved through the `filesystem` public interface against its `configured_root`. It must equal the record exactly (`resolved_root`, `absolute_path`) and stat as a regular file. No content is opened and no hash is checked. Resolution errors, stale records, missing, inaccessible or non-regular targets give `PROTECTED_LOCATION`. |
| Root and token | `workspace.root_key` must equal `root.root_key` exactly (`ROOT_KEY_MISMATCH`). There is no root registry or current-directory fallback. The ASCII pattern `[A-Za-z0-9_-]+` is rechecked, and on Windows reserved device names are rejected via `PureWindowsPath.is_reserved()` (Python 3.11); POSIX tokens face the pattern only. |
| Overlap | `PROTECTED_OVERLAP` if a protected canonical path equals, lies below or lies above the planned directory. This is a component relationship implemented with `PurePath.is_relative_to`, which is case-insensitive on Windows; per-directory case sensitivity is not accounted for. A root that also holds protected files is not rejected for that reason. |
| Creation | One exclusive `mkdir(parents=False, exist_ok=False)`. Any existing child (file, directory, symlink, dangling link, junction) gives `COLLISION` and is left untouched. There is no reuse, suffix or retry; a retry with the same token is again a collision. |
| Post-creation checks | Fresh strict re-resolution of the root, which must be unchanged as a string, and a root directory recheck. Fresh re-resolution of the child, which must equal the intended direct child exactly. `lstat` must show a real directory, not a symlink or a Windows reparse point, and a listing must show it empty. Expected failures give `WORKSPACE_CHANGED` with `created_directory` set; the directory is retained. |
| Failure precedence and mapping | Order: request type (plain `ValueError`), token syntax, root-key agreement, inventory, root syntax, strict root resolution and directory check, protected checks, overlap, `mkdir`, post-creation checks; the first failure wins. Before `mkdir`: a missing, non-directory or cyclic root (including `ELOOP` from the root stat and an exact `RuntimeError` cycle report) gives `INVALID_ROOT` with `created_directory` `None`, and root `PermissionError` gives `NOT_WRITABLE` (allocation denied; content-writing ability is not tested). A future writer must revalidate state, inventory and workspace and use its own exclusive output-creation protocol. *(2026-11-03: the writer below does this through `validate_allocated_workspace` and a single exclusive file creation; the allocation result is still not a capability.)*

### Workspace revalidation (`revalidation`, formerly `workspaces.validation`; ADR-025, Proposed)
`validate_allocated_workspace(workspace: AllocatedWorkspace) -> None` (module `workspaces.validation`, exported by the `workspaces` facade, which now has seven exports) rechecks an allocation record against the current allocation policy and filesystem. It is read-only: it does not call `allocate_workspace`, creates, opens, lists, modifies or removes nothing, and does not require the directory to be empty, so an earlier output does not block a later one. `allocation` is unchanged and does not import `validation`; `validation` imports only its `allocation` sibling (records and private policy helpers). Evidence: `tests/unit/test_workspace_validation.py` and the extended boundary tests (figures under "Exclusive WAV output" below). Status: implemented as read-only inspection.

| Element | Behaviour (as implemented) |
| --- | --- |
| Order | Argument type (plain `ValueError` before any I/O); directory token pattern and Windows reserved names; root-key agreement; mandatory inventory (current audio members plus fixed track-gain inputs, exactly equal metadata); root syntax; strict root resolution and directory check; recorded `resolved_root` equal to the fresh one and recorded `directory` equal to the recomputed direct child (exact strings); fresh protected-location checks in tuple order; overlap with the child; strict child resolution, which must equal the recorded directory; child `lstat` as a plain directory (no symbolic link, no Windows reparse attribute). The first failure wins. |
| Failures | `WorkspaceAllocationError` with the allocator's codes and `created_directory=None`. Stale, missing or redirected records and children give `WORKSPACE_CHANGED`. Root failures keep `INVALID_ROOT`, and a root permission denial keeps `NOT_WRITABLE`, although this operation writes nothing. Protected resolution failures give `PROTECTED_LOCATION`. The protected type check reuses the allocator helper unchanged, so an `ELOOP` from that stat propagates (the existing policy), while a link cycle met during protected resolution gives `PROTECTED_LOCATION`. Other unexpected errors propagate. |

Limits: a manually constructed record that matches the filesystem passes; this is inspection at call time, not proof of allocation provenance, ownership, history completeness or race-free confinement. Unrelated entries in the directory are neither inspected nor rejected.

### Exclusive WAV output (`wav_output`, formerly `wav_output.writing`; ADR-025, Proposed)
`autonomous_mixing.adapters.rendering.wav_output` (implementation module `writing`) creates one WAV/DOUBLE file from already computed float64 samples inside an allocated workspace and verifies it through the created handle. It applies no gain, sums no stems, selects no action, and builds no artifact, receipt or accepted state. It is a separate component, so the read-only `audio` facade is unchanged. It exports exactly four names:
- `WrittenWav`: frozen, 11 fields in this order: `workspace`, `path`, `sha256`, `byte_count`, `frame_count`, `sample_rate_hz`, `channel_count`, `container`, `subtype`, `render_spec`, `processing_spec`;
- `WavOutputFailureCode`, with eight members (lowercase values): `RESOURCE_LIMIT`, `ENCODING_FAILED`, `WORKSPACE_REJECTED`, `COLLISION`, `NOT_WRITABLE`, `WORKSPACE_CHANGED`, `IO_FAILED`, `VERIFICATION_FAILED`;
- `WavOutputError(code, message, *, created_file=None)`, a `ValueError` subclass with `.code`, `.created_file` and a code-prefixed message;
- `write_wav_output(workspace, filename, samples, *, render_spec, processing_spec, max_file_bytes, max_decoded_bytes) -> WrittenWav`.

Evidence (each source reported separately):
- Tests: `tests/unit/test_wav_output.py`, `tests/unit/test_workspace_validation.py`, the extended `tests/unit/test_application_infrastructure_boundaries.py` (retired in ADR-027 step M4; rules now in `tests/architecture/`), and `tests/unit/test_workspace_allocation.py` (only its facade-count test was adjusted to seven exports).
- Coordinator-reported full run: 2,778 passed, 3 platform skips: `tests/unit/test_artifact_locations.py:730` ("POSIX non-root only"), `tests/unit/test_wav_output.py:1181` ("POSIX keeps the default O_CREAT | O_EXCL opener") and `tests/unit/test_workspace_allocation.py:610` (POSIX device-name test).
- Independent correction review (raw-handle close correction): all 12 new regressions passed.
- Independent writer-focused run: 275 passed, 4 skips; three were junction skips caused by sandbox restrictions in the review environment and one was POSIX-only. Independent scoped lint and formatting passed.
- No fresh lockfile check: uv was unavailable; `pyproject.toml` and `uv.lock` are unchanged.
- Implementer-reported real Windows 11 evidence (not rerun by the coordinator except through the full suite): collisions with every entry form, including dangling links whose targets were not created; same-name concurrency over 10 rounds, each giving one success and one `COLLISION`; the bit-exact roundtrip; a real protected-file deletion after creation giving `WORKSPACE_CHANGED` with the file retained.
- Implementer-reported injected-only evidence (controlled doubles, not real-platform behaviour): short, zero and invalid write results; flush, seek, read and close failures; corrupted readback; descriptor-attachment and raw-handle close failures.

Status: implemented as a writer for one file per call. It reduces part of F3 (subtype mapping at this boundary) and contributes to non-overwriting output (QR-01, OP-02), but completes no requirement; requirement statuses are unchanged.

| Element | Behaviour (as implemented) |
| --- | --- |
| Arguments | Plain `ValueError` before any filesystem access for: a non-`AllocatedWorkspace`; a filename not exactly matching ASCII `[A-Za-z0-9_-]+\.wav` (lowercase extension, single leaf; on Windows also a reserved device stem under Python 3.11); samples that are not an exact `np.ndarray`, native float64, 2-D with at least one frame and one or two channels; wrong spec types; channel count different from `render_spec`; non-positive or non-built-in-`int` limits (no defaults). Unsupported `OutputContainer`/`SampleEncoding` values are rejected, never substituted. |
| Mapping | `OutputContainer.WAV` to soundfile `format='WAV'`, `SampleEncoding.FLOAT64` to `subtype='DOUBLE'`. The other `ProcessingSpec` fields are carried as descriptive configuration; the writer does not claim to have applied gain or summation. |
| Sample rate | Rates above `2**31 - 1` are rejected with plain `ValueError` during argument validation, before encoding, because soundfile would otherwise raise `OverflowError` (libsndfile stores the rate as a signed 32-bit int). This is a library representation limit, not a musical threshold or a change to `RenderSpec`. |
| Snapshot and limits | `frames × channels × 8` is checked against `max_decoded_bytes` before the finiteness scan and copy (`RESOURCE_LIMIT`; so an oversized non-finite input reports the limit first). Non-finite samples then raise plain `ValueError`. The input is copied into a private C-contiguous float64 array; the caller's array is not modified, and all later comparisons use only the snapshot. Read-only and strided inputs are accepted. No atomic snapshot is promised against concurrent mutation during copying. |
| In-memory encoding | Encoded into a `BytesIO` with explicit format, subtype, rate and channels; the encoding handle is closed before the payload is taken. The payload length is checked against `max_file_bytes` (`RESOURCE_LIMIT`) and against the 32-bit RIFF chunk-size field (`ENCODING_FAILED`; no switch to RF64/WAVEX). The payload is then decoded from memory and must show RIFF/WAVE, a consistent chunk size, `WAV`/`DOUBLE`, the declared rate, channels and frames, and samples bit-identical to the snapshot (compared as 64-bit patterns, so signed zeros, subnormals and finite values outside [-1, 1] are covered). `sf.LibsndfileError` or a mismatch here gives `ENCODING_FAILED`. No destination exists at this point. |
| Bounded I/O | Writes and reads are issued in requests of at most 1 MiB (an I/O buffer size, not a scientific threshold), so huge positive limits such as `sys.maxsize` or `10**100` never become oversized requests. Positive short writes are continued; a zero, `None` or out-of-range write result is `IO_FAILED`, not retried. Readback captures at most `max_file_bytes + 1` bytes. The limits bound accepted sample storage and payload size, not peak interpreter, libsndfile or `BytesIO` memory, CPU time or disk quota. |
| Exclusive creation | Workspace revalidation immediately before creation (failure gives `WORKSPACE_REJECTED`, no `created_file`). The destination is the recorded `workspace.directory / filename`. One `open(path, "x+b", buffering=0, opener=...)`; soundfile never receives the destination path, and there is no existence precheck, `"w"` mode, rename or replace. On Windows the opener calls `CreateFileW` with `CREATE_NEW | FILE_FLAG_OPEN_REPARSE_POINT` via ctypes and attaches a C descriptor with `msvcrt.open_osfhandle` (read/write, binary, not inheritable). POSIX uses the default exclusive opener (`O_CREAT | O_EXCL`). |
| Why the Windows opener | During implementation, plain `x+b` on Windows was found to follow a dangling file symbolic link and create its target outside the workspace. The owner approved the `CreateFileW` opener (Option A). With it, an existing final reparse point, dangling or not, is itself the existing entry. Intermediate path components are still resolved normally. |
| Collisions | Every existing form (file, directory, symbolic link, dangling link, junction) is rejected and left untouched; there is no overwrite or truncation. `FileExistsError` gives `COLLISION`. `IsADirectoryError` or `PermissionError` gives `COLLISION` only if a narrow `lstat` then confirms an entry; otherwise `PermissionError` gives `NOT_WRITABLE` and `IsADirectoryError` propagates. Missing or non-directory parents and `ELOOP` give `WORKSPACE_CHANGED`. Other errors propagate. |
| Readback and success | Write the payload, flush, seek to 0 and read back through the same handle. The captured bytes must equal the payload and are decoded again from memory against the snapshot (metadata, subtype, exact samples); mismatches or a libsndfile rejection give `VERIFICATION_FAILED`, oversized readback gives `RESOURCE_LIMIT`. The workspace is revalidated again (`WORKSPACE_CHANGED`), and the handle must close successfully (`IO_FAILED` otherwise) before `WrittenWav` is returned. `sha256`, `byte_count`, `container` and `subtype` come from the captured readback, not from the encoding buffer. |
| `WrittenWav` | Construction validates types, a 64-digit lowercase hex `sha256`, positive built-in-`int` counts, and, beyond the written design, cross-checks `sample_rate_hz` and `channel_count` against `render_spec`. No I/O and no array field. It retains the original workspace and spec objects. It is a descriptive record, not a persisted artifact, success verdict, capability or guarantee about later path contents. |
| Retained files | Expected failures after a successful open carry `created_file`; the file (empty, partial or complete) is retained. Nothing is deleted, renamed, replaced, retried or cleaned up; a retry with the same filename collides. `created_file` reports a known creation, not current existence or permission to delete. |
| Close-error priority | On a failure after open, the owned handle is closed. If that close also fails with an ordinary exception, the primary failure is re-raised; a note is added only when the primary is a `WavOutputError`. Foreign primary exceptions propagate unchanged. A sole close failure on the success path gives `IO_FAILED` with `created_file`. Correction (reviewed): if `open_osfhandle` fails after `CreateFileW` created the file, the raw handle is closed, and if that close also fails, the original attachment exception is re-raised as the same object, without notes or wrapping. |

Limits:
- Exact sample preservation does not imply reproducible WAV bytes or hashes. libsndfile 1.2.2 writes a PEAK chunk containing a timestamp, so bytes and SHA-256 can differ between encodings of identical samples. (A one-off documentation probe on 2026-11-03 with soundfile 0.14.0 and libsndfile 1.2.2 confirmed a PEAK chunk and different bytes for two encodings of identical samples about one second apart; this is not regression coverage.)
- An unexpected descriptor-attachment failure on Windows may leave an empty file without `created_file`; it is observable only on disk.
- Ordinary secondary close errors preserve the primary failure, but a secondary `KeyboardInterrupt` or `SystemExit` during that close may supersede it.
- The Windows opener uses the C runtime's default sharing (other readers and writers are not denied), so the created handle is no exclusive-access lock.
- Parent paths are not pinned. There is no race-free confinement, fsync durability, atomic publication, two-output transaction, lock or complete history guarantee.
- No connected DSP processing adapter or execution pipeline exists; nothing imports `wav_output` yet. *(Superseded 2026-11-03, later: the gain/full-mix processor below now imports `wav_output`; no execution pipeline exists.)*
- Subtype mapping is implemented at this writer boundary only. F2 is unaffected and F4 stays open.
- No requirement is completed, and no perceptual or research-performance result follows. The tests use tiny analytical arrays, not evaluation data.

### Gain/full-mix renderer (`gain_mix`, formerly `processing.gain_mix`; ADR-026, Accepted)
**Implemented** (evidence: `tests/unit/test_gain_mix_processor.py`; boundary rules in `tests/unit/test_application_infrastructure_boundaries.py` (retired in ADR-027 step M4; rules now in `tests/architecture/`)). This is the first `Renderer` implementation. It adds no numerical behaviour: it composes the verifier, the kernels and the writer. The design and decisions D1–D5 are in [`gain-mix-processor-design.md`](gain-mix-processor-design.md).

| Aspect | Behaviour |
| --- | --- |
| Interface | `adapters.rendering.gain_mix` exports `GAIN_MIX_PROCESSOR` (`VersionRef("autonomous_mixing.gain_mix_processor", "1")`), `ProcessingLimits(max_file_bytes, max_decoded_bytes)` and `GainMixProcessor(workspace: AllocatedWorkspace, limits)`. It satisfies the port structurally. |
| Binding | The caller allocates the workspace; one processor serves one execution. Inputs are looked up in `workspace.request.protected_locations` and must equal the plan's records. Wiring errors (wrong types, foreign workspace or before revision, missing or differing locations, inputs incompatible with the render settings) raise plain `ValueError` before any file access. |
| Processing | Verify the fixed target input, then each non-target current stem in recipe order; apply the absolute gain to the fixed input; sum in recipe order with the new target in place of the obsolete one; write `target.wav`, then `mix.wav`. The obsolete target stem and the current mix are never opened. |
| Outcome | `RenderedCandidate` with locations `<directory_token>/<filename>` relative to the output root, the writer's readback hash and evidence citing the fixed input (target) or the new target plus non-target stems (mix). Expected failures return `RenderFailure(FAILED, ...)` with code `input_verification_failed`, `processing_failed` or `output_failed:<writer code>`; retained files are named. Unexpected exceptions propagate. |

Limits:
- Input and kernel failures leave no output files; a mix-write failure retains a verified `target.wav`. There is no two-output transaction and no cleanup.
- Output hashes are not reproducible across runs (PEAK chunk, above); samples are. Input bytes are verified at capture time only.
- Peak memory grows with the number of stems held at once and is not bounded by the limits.
- Environment provenance is not recorded (F3 stays open). No execution service, receipt or candidate-state assembly exists, and nothing imports `processing` yet.
- No requirement is completed, and no perceptual or research-performance result follows. Tests use tiny analytical arrays, not evaluation data.
