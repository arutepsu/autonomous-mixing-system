# Architecture

## Confirmed decisions
- Offline Python processing of synchronized WAV stems; modular monolith with a CLI; no DAW plugin in M0 ([ADR-001](../decisions/0001-offline-python-workflow.md)).
- Deterministic audio analysis and DSP; Claude proposes structured actions but never performs measurements or audio processing ([ADR-001](../decisions/0001-offline-python-workflow.md)).
- Single agent with deterministic orchestration: application code controls the loop, validates proposals, executes DSP and verifies results ([ADR-004](../decisions/0004-single-agent-deterministic-orchestration.md)).
- uv-managed environment, Python 3.11 ([ADR-002](../decisions/0002-uv-dependency-management.md)).
- Track-role-agnostic design: stems carry declared roles; components must not assume specific instruments such as kick/bass. Problem-specific components are added only in their roadmap phase; analysis parameters and thresholds must be configurable and documented ([ADR-006](../decisions/0006-research-first-development-policy.md)).

## Target pipeline (planned)
Audio I/O -> deterministic features -> detectors -> structured problem candidates -> Claude proposal (`decision_agent`) -> action validator -> DSP execution -> verification -> accept/revert -> experiment report.

Hidden-reference boundary ([ADR-010](../decisions/0010-hidden-reference-boundary.md), requirements SR-10): everything up to accept/revert is runtime and never reads the original reference audio or defect-injection ground truth. Run records hold runtime inputs and the action history. Research evaluation joins them with the separately stored hidden evaluation data only after execution.

## Implemented (M0)
M0 implements only Audio I/O -> features -> descriptive JSON report. Do not claim masking detection from overlap measures alone.

| Module | Responsibility |
| --- | --- |
| `autonomous_mixing.audio.io` | Load WAV stems as float64 `(frames, channels)`; reject non-WAV, unreadable, too-short (< 2048 frames), > 2-channel and non-finite input; require equal sample rate and frame count for a pair. |
| `autonomous_mixing.audio.features` | Mono fold-down, RMS/peak dBFS, STFT magnitudes, band-power and temporal-coactivity proxies. |
| `autonomous_mixing.audio.analysis` | `analyze_pair`: combines the above into the `m0.1` report dict, including input SHA-256 hashes. |
| `autonomous_mixing.cli` | `autonomous-mixing analyze`: writes the JSON report; validation errors exit with code 2 and a one-line message. |
| `scripts/generate_test_audio.py` | Deterministic synthetic kick/bass stems, formerly used for manual smoke runs (not perceptual ground truth). No test depends on it; under review per ADR-006. |

Analysis parameters (STFT 2048/512, 30–200 Hz band, 10 % coactivity threshold) are fixed in code. `configs/analysis.yaml` documents them as a proposed manifest but is **not read** by the code yet.

**Known deviations from ADR-006 (M0):** the two inputs are named `kick`/`bass` in the CLI, `analyze_pair` and the report keys, and the parameters above are hardcoded. Retained unchanged until reviewed; do not extend this pattern.

## Infrastructure (in-memory numerics, read-only location resolution and WAV verification; no processing adapter or writer)
Heading revised 2026-10-22: the earlier label "Infrastructure kernels (implemented in-memory numerics; no adapter)" is superseded because the package now also verifies existing WAV files read-only. It still contains no processing adapter, WAV writer or workspace allocator. Numerical kernels, file verification and future writing are separate concerns below. Heading revised again 2026-11-02 to name read-only location resolution (`infrastructure.filesystem`); the package still contains no processing adapter, WAV writer or workspace allocator.

### Numerical kernels (`dsp`)
`autonomous_mixing.infrastructure.audio` (module `dsp`) implements the numerical rules of `ProcessingSpec` (ADR-021: FLOAT64, DB_AMPLITUDE, RECIPE_SEQUENTIAL, PRESERVE) on in-memory NumPy arrays; the container and sample-encoding settings belong to the future file adapter. Neither the domain nor the application imports the package. Evidence: `tests/unit/test_audio_dsp.py` (126 test cases passed; full suite 1,218 passed; ruff lint and scoped formatting passed; independent review, 2026-10-22). Status: implemented for the in-memory kernels only; they contribute to FR-08, FR-17, QR-01 and QR-02 but complete none of them.

| Function | Numerical rule |
| --- | --- |
| `apply_absolute_gain(input_samples, gain_db)` | `gain_db` must be exactly a built-in `int` or `float` (`bool`, NumPy scalars including `np.float64`, and `int`/`float` subclasses are rejected before any conversion or arithmetic). Factor `10 ** (gain_db / 20)` in built-in arithmetic must be finite and strictly positive: overflow or rounding to zero is rejected even for silent input; positive subnormal factors are allowed. Multiplies the fixed input; a non-finite product is rejected. Repeated calls on the same input do not compound. |
| `sum_stems(stems)` | Nonempty exact `tuple` of identically shaped arrays. A new float64 zero accumulator receives each stem in tuple order, with a finiteness check after every addition. No reordering, stacked or compensated summation, normalization, clipping or limiting. |
| Shared input and output rules | Inputs must be exact `np.ndarray`, native-endian float64, 2-D `(frames, channels)`, at least one frame, one or two channels, finite. Read-only, non-contiguous and negative-stride views are accepted. No cast, reshape, broadcast, padding or fold-down; finite values outside [-1, 1] are preserved. Inputs are never mutated, also on failure; outputs are newly allocated. Floating-point conditions are handled under a local `np.errstate`, and the caller's NumPy error settings are restored. Expected failures raise `ValueError`. |

Limits: no WAV processing adapter, execution service or connected correction pipeline exists, and only tests call the kernels. Array immutability does not establish source-file protection (QR-01); F2 and F4 remain open (see Open questions). A fixed operation order does not promise bitwise-identical results across platforms, and no cross-platform identity is claimed. The tests use synthetic numerical arrays; no perceptual or research-performance result follows from them. No test yet enforces the infrastructure package's own import boundary. *Superseded (2026-10-22, ADR-022): source-import rules for the existing infrastructure modules are now enforced; see Import boundaries below.*

### Read-only WAV artifact verification (`verification`)
`verify_wav_artifact(artifact, *, max_file_bytes, max_decoded_bytes) -> VerifiedAudio` checks one existing file against its `AudioArtifact` metadata. It writes, renames and removes nothing. It imports the `domain.project` interface (`AudioArtifact`) and soundfile/libsndfile. Evidence: `tests/unit/test_audio_verification.py` (87 test cases passed, no skips; full suite 1,305 passed; ruff lint and scoped formatting passed; independent review, 2026-10-22). Status: implemented for read-only verification of a single artifact. It contributes to QR-01, QR-02, QR-03, FR-02 and FR-17 but completes none of them; requirement statuses are unchanged.

| Element | Behaviour |
| --- | --- |
| Arguments | `artifact` must be an `AudioArtifact`; both limits must be positive built-in `int`s, with no default and no scientific meaning. Invalid arguments raise plain `ValueError` before any file access. |
| Path | `artifact.location` must be an absolute local path. Relative, URI-style and UNC/network/device-namespace forms (and NUL characters) are rejected lexically as `UNSUPPORTED_PATH`. |
| Capture | Regular-file check on the pathname, one `open`, regular-file check on the opened handle, then a bounded read of at most `max_file_bytes + 1` bytes. Reads are chunked at no more than 1 MiB each (an I/O buffer size, not a scientific threshold), so arbitrarily large positive limits are accepted while the total-read bound is kept. A larger payload is rejected (`RESOURCE_LIMIT`). |
| Hash | The SHA-256 of the captured payload must equal `artifact.content_hash` before any decoding (`HASH_MISMATCH`). |
| Decode | From the same captured bytes in memory; the path is not opened a second time. The container is detected from content, not the file extension, and must be libsndfile `WAV`, `WAVEX` or `RF64`. Declared sample rate, channel count and frame count must match (`METADATA_MISMATCH`). The file needs at least one frame and one or two channels. Decoded storage (frames × channels × 8 bytes) is checked against `max_decoded_bytes` before decoding. Fewer decoded frames than inspected, or unreadable content, give `INVALID_WAV`. Samples must be finite (`NONFINITE_SAMPLES`). |
| Result | `VerifiedAudio(artifact, samples, container, subtype, verified_sha256)`: frozen, with identity equality. `samples` is a native float64 `(frames, channels)` array returned read-only, without normalization, clipping, resampling, padding or fold-down. `container` and `subtype` are libsndfile's names for the detected format. |
| Failures | Expected file and content failures raise `ArtifactVerificationError`, a `ValueError` subclass whose `.code` is a `VerificationFailureCode`: `UNSUPPORTED_PATH`, `NOT_FOUND`, `NOT_READABLE`, `NOT_REGULAR_FILE`, `RESOURCE_LIMIT`, `HASH_MISMATCH`, `INVALID_WAV`, `METADATA_MISMATCH`, `NONFINITE_SAMPLES`. |

Limits:
- Verification establishes the identity of the captured payload only. It does not establish that the pathname still holds those bytes afterwards; a future processor must consume the returned samples or reverify whatever it reads later.
- `verify_wav_artifact` has no directory confinement and no protection against aliases, symbolic links, junctions or other reparse points. Neither entry point provides race-free capture. (2026-11-02: `verify_resolved_wav_artifact` adds canonical root containment at resolution time only; see below.)
- The byte limits bound the captured payload and the returned sample storage only. They do not bound total process or decoder memory.
- The read-only array flag guards against accidental mutation; it is not a security boundary.
- Existing records and fixtures use relative locations such as `outputs/{id}.wav`, which `verify_wav_artifact` rejects. *Superseded (2026-11-02): such locations can now be verified through `resolve_artifact_location` and `verify_resolved_wav_artifact` with an explicit root (see below); `verify_wav_artifact` itself still rejects them.*
- No workspace allocator, WAV writer, processing adapter or connected execution pipeline exists yet. F4 (write protection, workspace confinement) and F2 (acceptance/validation evidence linked to the candidate state) remain open.
- No perceptual or research-performance result is established.
- Platform: tested on Windows. soundfile 0.14.0 is the version pinned in `uv.lock`; libsndfile 1.2.2 is taken from the implementation report and is not recorded in the lockfile. The POSIX-specific `IsADirectoryError` branch was not exercised on a real filesystem. Permission failures and a non-regular opened handle were exercised only via test doubles.

### Read-only artifact-location resolution (`filesystem`; ADR-023, Proposed)
`autonomous_mixing.infrastructure.filesystem` (implementation module `locations`) owns local interpretation of artifact locations. It exports exactly four names:
- `ResolvedArtifactLocation(artifact, configured_root, resolved_root, absolute_path)`;
- `LocationResolutionFailureCode`, with seven codes: `UNSUPPORTED_PATH`, `INVALID_ROOT`, `NOT_FOUND`, `NOT_READABLE`, `OUTSIDE_ROOT`, `RESOLUTION_LOOP`, `STALE_RESOLUTION`;
- `LocationResolutionError`, a `ValueError` subclass with `.code` and a message prefixed by the code value;
- `resolve_artifact_location(artifact, *, root)`.

The resolver inspects filesystem metadata only. It opens no file content and writes, creates, renames or removes nothing.

Evidence:
- Tests: `tests/unit/test_artifact_locations.py`, `tests/unit/test_resolved_audio_verification.py` and the extended `tests/unit/test_application_infrastructure_boundaries.py` and `tests/unit/test_application_component_compatibility.py`.
- Implementer rerun: full suite 1,870 passed, 1 skipped (the POSIX-only permission test).
- Independent review: 1,866 passed, 5 skipped, because four Windows junction tests could not run under the review environment's sandbox permissions. Ruff lint, scoped formatting and CLI help passed.

Status: implemented as read-only resolution and verification. It contributes to existing artifact-verification and provenance requirements but completes none of them; requirement statuses are unchanged.

| Element | Behaviour (as implemented) |
| --- | --- |
| Record | `ResolvedArtifactLocation` is a frozen dataclass. `artifact` is the original `AudioArtifact` object: its location stays as written, including relative, and no field is changed or copied. `configured_root` is the caller's root string verbatim. `resolved_root` and `absolute_path` are strings produced by strict resolution. Construction checks types and non-blank strings only, without filesystem access. A record therefore certifies neither existence nor canonicality, may be stale, and is not an authorization, capability or security token. |
| Arguments | `artifact` must be an `AudioArtifact` and `root` a non-blank `str` (a `Path` is rejected); otherwise plain `ValueError` is raised before filesystem access. There is no default root, root registry, current-directory fallback, URI decoding, environment-variable or tilde expansion, or foreign-platform translation. |
| Lexical policy (native platform only; first the root, then the location) | Raises `UNSUPPORTED_PATH` for: NUL characters; two leading separators of either kind (treated as UNC/network/device on every platform); URI-style prefixes (the verifier's pattern, two or more scheme characters followed by `:`); any `..` component. The root must be fully absolute. On Windows it also rejects drive-relative and root-relative forms, and it intentionally rejects colons outside the drive prefix, including alternate data streams. On POSIX it also rejects Windows drive syntax. The URI-style, Windows-drive and two-leading-separator exclusions are intentional supported-input restrictions applied on all platforms. Valid POSIX names such as `take:1.wav`, `a:b.wav` or `//`-prefixed paths are therefore outside the supported input form; they are not invalid POSIX names. `.` components are allowed. |
| Resolution | The root is resolved strictly and must be an existing directory; a root reached through a link is allowed, and `resolved_root` records the actual directory. Relative locations are joined to the resolved root; absolute locations are used directly. The candidate is resolved strictly and must exist. A directory candidate can resolve, and the verifier rejects it later. |
| Containment | Exact path-component comparison (component prefix, not string prefix) after strict canonical resolution of both root and candidate. A target equal to the root is rejected as `OUTSIDE_ROOT`. Links and junctions whose canonical target lies inside the root are allowed, including an absolute alias outside the root pointing inside it; canonical targets outside the root are rejected. |
| Failures and precedence | Order: argument checks, root lexical check, location lexical check, strict root resolution and directory check, strict candidate resolution, containment; the first failure wins. A missing root or a root that is not a directory gives `INVALID_ROOT`. A missing candidate or intermediate component gives `NOT_FOUND`, even when the text looks outside the root. `PermissionError` gives `NOT_READABLE`. An `ELOOP` `OSError`, or an exception of exact type `RuntimeError` (Python 3.11 pathlib's cycle report), from `Path.resolve` gives `RESOLUTION_LOOP`. Other `OSError`s and other exceptions, including `RuntimeError` subclasses, propagate unchanged. Exceptions are mapped around the individual resolve/stat calls only, not around the whole resolver. |

**Verifier entry point.** `verify_resolved_wav_artifact(location, *, max_file_bytes, max_decoded_bytes) -> VerifiedAudio` (in `audio.verification`) works in five steps:
1. It validates the record type and both limits before any filesystem access.
2. It resolves `location.artifact` afresh against `location.configured_root`. Resolution errors propagate unchanged as `LocationResolutionError`.
3. It raises `STALE_RESOLUTION` before any content open if the fresh `resolved_root` or `absolute_path` differs from the record's by exact string comparison. A canonically equal but textually different record is therefore stale.
4. It verifies the freshly resolved path through the private capture/hash/decode pipeline it shares with `verify_wav_artifact`, against the original artifact's declared hash and metadata.
5. The result's `VerifiedAudio.artifact` is the original object, and the resolution record is not retained in it.

After successful resolution, disappearance or permission failure give the existing audio capture codes. Changed bytes at the same path give `HASH_MISMATCH`. Path equality does not prove file identity.

`verify_wav_artifact` keeps its API and behavior: absolute paths only, no root confinement. The `infrastructure.audio` facade now has seven exports.

Implementation choices recorded as observed in code (not all have a dedicated test):
- Supported-input restrictions, intended and applied on all platforms: the verifier's URI pattern, Windows drive syntax and two leading separators (UNC form) are excluded. Valid POSIX names such as `take:1.wav`, `a:b.wav` or `//`-prefixed paths are outside the supported input form.
- On Windows, colons outside the drive prefix, including alternate data streams, are rejected as intended.
- Containment compares path components exactly after strict canonical resolution. The independent reviewer's native Windows casing probe passed: a differently cased but equivalent path resolved within the root. That was a one-off review probe, not regression coverage; the suite has no dedicated casing test.
- The stale check compares exact strings.
- The Windows `..` check matches exact components only (forms such as `.. ` or `...` are not lexical traversal), and canonical containment is the backstop.
- Only an exact `RuntimeError` maps to `RESOLUTION_LOOP`.

Limits:
- Strict resolution and containment describe the filesystem as observed during the calls. They give no race-free confinement, link immutability, hard-link uniqueness, exclusive access, write protection or source protection.
- There is no workspace allocation, WAV writing, processing adapter or connected execution pipeline.
- F4 and F2 remain open.
- No perceptual or research-performance result follows.
- Platform evidence (implementer, Windows 11 with Developer Mode) covers real file and directory symlinks and junctions: inside→inside is allowed, inside→outside is rejected, root aliases resolve, and real symlink and junction cycles are detected. Permission failures, the `ELOOP` branch and propagation of unexpected errors were exercised only through test doubles, so they are not real-platform evidence. The real POSIX permission test was skipped on Windows.

### Import boundaries (source-level; ADR-022)
Enforced by `tests/unit/test_application_infrastructure_boundaries.py` (2026-10-22). `infrastructure/audio` stays one component with two focused modules; no subpackages were created.

| Module | Allowed source imports |
| --- | --- |
| `autonomous_mixing.infrastructure` | none (descriptive initializer only) |
| `autonomous_mixing.infrastructure.audio` | re-exports of `dsp` and `verification` only (seven names since 2026-11-02; previously six) |
| `infrastructure.audio.dsp` | standard library and NumPy only; not the domain, the application, soundfile, `verification` or `filesystem` |
| `infrastructure.audio.verification` | standard library, NumPy, soundfile, the `domain.project` interface and, since 2026-11-02, the `filesystem` interface (never `filesystem.locations` directly); not the application or `dsp` |
| `autonomous_mixing.infrastructure.filesystem` | re-exports of `locations` only (four names) |
| `infrastructure.filesystem.locations` | standard library and the `domain.project` interface only; not audio, the application, NumPy or soundfile |

Rows for `filesystem` and `locations`, and the `filesystem` permission for `verification`, were added on 2026-11-02 (ADR-023, Proposed). The enforcing tests also check the real import edges, re-export-only initializers and new fresh-process import orders.

Neither leaf imports the M0 audio package, the CLI, presentation or provider code. These are source-import rules, not a runtime-isolation claim: the `audio` facade loads both leaves, so importing it also loads soundfile. Unclassified future infrastructure modules fail the test until their rule is designed. No processing adapter exists; a future adapter that implements an application port will need its allowed imports and filesystem dependencies designed explicitly, and nothing here establishes filesystem protection or workspace confinement.
