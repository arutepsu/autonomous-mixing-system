# ADR-025 — exclusive WAV/DOUBLE output in a separate infrastructure component, with read-only workspace revalidation (2026-11-03)
- Status: Proposed; awaiting owner review of the implementing stage.
- Decision: write already computed float64 samples to one exclusively created WAV/DOUBLE file inside an allocated workspace, encode and check the payload in memory before the destination exists, verify the bytes read back through the created handle, and retain the file after any failure.
  1. Separate component: `autonomous_mixing.infrastructure.wav_output` (initializer re-exporting `writing` only) exports exactly `WrittenWav` (frozen, 11 fields: `workspace`, `path`, `sha256`, `byte_count`, `frame_count`, `sample_rate_hz`, `channel_count`, `container`, `subtype`, `render_spec`, `processing_spec`), `WavOutputFailureCode` (`RESOURCE_LIMIT`, `ENCODING_FAILED`, `WORKSPACE_REJECTED`, `COLLISION`, `NOT_WRITABLE`, `WORKSPACE_CHANGED`, `IO_FAILED`, `VERIFICATION_FAILED`), `WavOutputError(code, message, *, created_file=None)` (`ValueError` subclass) and `write_wav_output(workspace, filename, samples, *, render_spec, processing_spec, max_file_bytes, max_decoded_bytes) -> WrittenWav`. `writing` imports only the standard library, NumPy, soundfile and the `domain.project`, `domain.observation` and `workspaces` public interfaces. `audio` and `filesystem` imports load neither `workspaces` nor `wav_output`; nothing imports `wav_output` yet. The read-only `audio` facade is unchanged. This extends the source rules of ADR-022 to ADR-024.
  2. Public workspace revalidation: `validate_allocated_workspace(workspace: AllocatedWorkspace) -> None` in a new `workspaces.validation` module (the `workspaces` facade now has seven exports). It is read-only, never calls the allocator, does not require an empty directory, and reuses the allocator's codes and private policy helpers; `allocation` is unchanged and does not import it.
  3. Explicit mapping and inputs: `OutputContainer.WAV` to `format='WAV'`, `SampleEncoding.FLOAT64` to `subtype='DOUBLE'`; no fallback. Filenames are single ASCII leaves `[A-Za-z0-9_-]+\.wav` (Windows reserved stems rejected). Samples follow the numerical kernels' input contract and are copied into a private snapshot. Both byte limits are required positive built-in `int`s; I/O requests are at most 1 MiB, so huge limits are supported.
  4. In-memory encoding first: the payload is encoded into memory, checked against `max_file_bytes` and the 32-bit RIFF size field, and decoded again with metadata, subtype and bit-exact samples (signed zeros, subnormals and finite overrange values included) before any destination exists.
  5. Exclusive final-file creation: revalidate the workspace immediately before creation, then one `open(path, "x+b", buffering=0, opener=...)` on the recorded `workspace.directory / filename`. soundfile never opens the destination path. On Windows the opener calls `CreateFileW` with `CREATE_NEW | FILE_FLAG_OPEN_REPARSE_POINT` through ctypes and attaches a descriptor with `msvcrt.open_osfhandle`; POSIX uses the default exclusive opener. Every existing entry form (file, directory, symbolic link, dangling link, junction) is a collision and is neither overwritten nor truncated.
  6. Readback evidence: write in bounded chunks, flush, seek and read back through the created handle; compare the captured bytes with the payload, decode them again, revalidate the workspace and close the handle successfully before reporting success. SHA-256, size, container and subtype describe the captured bytes, not the encoding buffer.
  7. Retained failures: expected failures after the open carry `created_file`; nothing is deleted, renamed, retried or cleaned up. A primary failure is kept when an ordinary secondary close error occurs (with a note only on `WavOutputError`); foreign exceptions propagate unchanged. If descriptor attachment fails and the raw-handle close also fails, the original attachment exception is re-raised as the same object.
- Source: owner-approved design "Exclusive WAV output" and its implementation plan (2026-11-02), kept in the owner's planning workspace; owner approval of the Windows `CreateFileW` opener (Option A) during implementation; audit findings F3 and F4; open question on the writer's no-overwrite protocol in `docs/architecture/overview.md`.
- Rationale: execution needs a file boundary that realizes the `ProcessingSpec` container and encoding without overwriting existing outputs and with evidence of what was actually written. Exclusive creation at the final name gives clear collision semantics without a publication or recovery protocol. Encoding and checking in memory means encoder failures and size rejections leave no destination. Reading back through the created handle avoids trusting the encoding buffer or reopening a pathname that may since have changed. The Windows opener was added because plain `x+b` was found during implementation to follow a dangling file symbolic link and create its target outside the workspace. Rejected or deferred: temporary files with no-overwrite publication (needs a separate publication and recovery protocol); adding writing to the read-only `audio` facade; passing the destination path to soundfile.
- Consequences:
  - Implementation deviations from the written design: sample rates above `2**31 - 1` are rejected with plain `ValueError` during argument validation, before encoding, because soundfile raises `OverflowError`; `WrittenWav` also cross-checks sample rate and channel count against `render_spec`.
  - Exact sample preservation does not imply reproducible WAV bytes or hashes: libsndfile 1.2.2 writes a PEAK chunk with a timestamp, so bytes and hashes can differ between encodings of identical samples.
  - An unexpected descriptor-attachment failure may leave an empty file without `created_file`. A secondary `KeyboardInterrupt` or `SystemExit` during a failure-path close may supersede the primary failure.
  - Failed writes leave files behind, and a retry with the same filename collides; cleanup and recovery are separate future policies. `WrittenWav` is a descriptive record, not an artifact, verdict or capability.
  - Parent paths are not pinned. There is no race-free confinement, fsync durability, atomic publication, two-output transaction, lock or complete history guarantee.
  - No connected DSP processing adapter or execution pipeline exists. Subtype mapping is implemented at this writer boundary only (F3 narrowed); F4 stays open and F2 is unaffected. No requirement is completed or changes status; no perceptual or research-performance result follows.
  - Open questions: hash reproducibility policy; Windows error 1921 propagating as an unexpected error; the empty-file-on-attachment-failure limit.
