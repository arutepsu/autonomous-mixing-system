# ADR-023 — explicit-root, read-only artifact-location resolution with a separate provenance record (2026-11-02)
- Status: Proposed; awaiting owner review of the implementing stage.
- Decision: resolve `AudioArtifact.location` against an explicit, caller-supplied local root in a new read-only infrastructure component, record the result separately from the unchanged artifact, and verify WAV content only after fresh re-resolution.
  1. Ownership: `autonomous_mixing.infrastructure.filesystem` (initializer re-exporting `locations` only) owns local location interpretation. Public names: `ResolvedArtifactLocation(artifact, configured_root, resolved_root, absolute_path)`, `LocationResolutionFailureCode` (`UNSUPPORTED_PATH`, `INVALID_ROOT`, `NOT_FOUND`, `NOT_READABLE`, `OUTSIDE_ROOT`, `RESOLUTION_LOOP`, `STALE_RESOLUTION`), `LocationResolutionError` (`ValueError` subclass with `.code`), `resolve_artifact_location(artifact, *, root)`. `locations` imports only the standard library and the `domain.project` interface; `audio.verification` may import the `filesystem` interface, never `filesystem.locations`; `dsp` is unchanged. This extends the infrastructure source rules of ADR-022.
  2. Separate provenance record: the original `AudioArtifact` object is kept as is (a relative location stays relative; no field changes, no copy). `configured_root` keeps the caller's string verbatim; `resolved_root` and `absolute_path` come from strict resolution. Record construction checks types and non-blank strings only; a record is not a capability, authorization or security token and may be stale.
  3. Explicit root, native paths: the root must be a non-blank, fully absolute native local path that strictly resolves to an existing directory (reaching it through a link is allowed). No default root, registry, current-directory fallback, URI decoding, environment-variable or tilde expansion, or foreign-platform translation. Lexically rejected (`UNSUPPORTED_PATH`): NUL, two leading separators, URI-style prefixes, any `..` component, on Windows drive-relative/root-relative forms and colons outside the drive prefix (alternate data streams are intentionally rejected), on POSIX Windows drive syntax. The URI-style, Windows-drive and two-leading-separator (UNC) exclusions are intentional supported-input restrictions on all platforms. Valid POSIX names such as `take:1.wav`, `a:b.wav` or `//`-prefixed paths are outside the supported input form, not invalid POSIX names.
  4. Canonical containment: relative locations are joined to the resolved root, absolute ones used directly; the candidate must strictly resolve and, by exact path-component comparison after strict canonical resolution, be a descendant of the resolved root (root equality rejected). Links and junctions resolving inside the root are allowed; canonical targets outside are rejected (`OUTSIDE_ROOT`).
  5. Failures: fixed order (arguments, root lexical, location lexical, strict root resolution and directory check, strict candidate resolution, containment), first failure wins. Only the expected missing, permission and cycle conditions are mapped (`ELOOP` `OSError` and exact `RuntimeError` from `Path.resolve` to `RESOLUTION_LOOP`); other exceptions propagate.
  6. Fresh re-resolution: `audio.verification.verify_resolved_wav_artifact(location, *, max_file_bytes, max_decoded_bytes)` validates its inputs before filesystem access, re-resolves the original artifact against `configured_root`, raises `STALE_RESOLUTION` before opening content if the fresh root or path string differs, and then runs the private capture/hash/decode pipeline shared with `verify_wav_artifact`. It returns `VerifiedAudio` with the original artifact object.
  7. Unchanged guarantees: `verify_wav_artifact` keeps its signature, absolute-path-only policy (no root confinement), error order, codes, bounded single-open capture, hash-before-decode and numerical rules. The existing six audio exports and their identities are unchanged; one export is added.
- Source: owner-approved design "Read-only artifact-location resolution" and its implementation plan (2026-11-02), kept in the owner's planning workspace; open question on relative artifact locations in `docs/architecture/overview.md` (2026-10-22).
- Rationale: records and fixtures use portable relative locations (e.g. `outputs/{id}.wav`), while the verifier accepts only absolute paths. A separate record bridges both without altering artifact metadata, so checkpoint metadata comparisons (ADR-015, ADR-020) stay exact and provenance (QR-03) can name the root actually used. Rejected alternatives: replacing `AudioArtifact.location` on a copied artifact (different metadata for the same identity, breaking exact metadata comparisons); requiring absolute locations at registration (machine-dependent stored metadata and a registration flow that does not exist). Canonical containment with permitted inside-root links follows the resolved target rather than imposing a blanket link ban; rejecting `..` lexically removes textual traversal before any filesystem access, with containment as backstop.
- Consequences:
  - Relative locations can be verified only with an explicit root; callers keep the resolution record themselves. No run persistence or execution evidence record carries it yet.
  - Resolution and containment describe the filesystem observed during the calls: no race-free confinement, link immutability, hard-link uniqueness, exclusive access, write protection or source protection follows. Audit findings F2 and F4 remain open; F3 is unchanged.
  - The stale check compares exact strings: a canonically equal but textually different record is `STALE_RESOLUTION`. Containment compares components exactly after strict canonical resolution. An independent native Windows casing probe passed (a differently cased but equivalent path resolved within the root); it was a one-off review probe, and the suite has no dedicated casing test.
  - Inputs outside the supported form are rejected on every platform, including valid POSIX names such as `take:1.wav`, `a:b.wav` or `//`-prefixed paths.
  - No workspace allocation, WAV writing, processing adapter or execution pipeline is added; no requirement is completed or changes status; no perceptual or research-performance result follows.
  - Open questions: who supplies and records the root in a run; workspace allocation for outputs; race and alias handling beyond resolution-time containment.
