# ADR-027 — hexagonal architecture around a MAPE-K control loop, with immutable records (2026-11-03)
- Status: Accepted 2026-11-03 by the owner, after two independent Codex reviews; the M1 pilot decides whether the remaining migration steps proceed as planned. No code had been moved at acceptance. Amended before acceptance on 2026-11-03 (owner decisions MD-3 and MD-4 in [`adr-027-migration-plan.md`](../architecture/adr-027-migration-plan.md)): points 2, 3 and 4 no longer have `core.measurement` and `core.decision` packages, and point 8 moves code before the loop is built. Amended again on 2026-11-03 after an independent Codex review: points 2 to 4 put every data type, including port requests and responses, in `core.records` (this narrows the first amendment: ports now own their protocols and response checks, not the types), point 4 states that the import rules do not replace SR-10's runtime-input tests, point 5 makes `slots=True` a separate optional step, point 8 classifies the migration steps and requires a guarantee ledger, and the immutability rationale is narrowed. Approval of the direction is conditional on a successful M1 pilot (migration plan). Amended a third time on 2026-11-03 after Codex's second review: point 2 limits `core.records` to core-facing business and port records (adapter-local data stays in adapters), requires an acyclic module graph inside `core.records`, and states that ports exchange request/response types whose definitions live in records; point 5 applies to core records only.
- Decision: reorganize the system from horizontal domain/application/infrastructure layers into a hexagonal (ports-and-adapters) modular monolith whose core is the mixing control loop. The binding rules for contributors are kept in [`engineering-conventions.md`](../project/engineering-conventions.md); this ADR records the decision and its reasons.
  1. Architectural style, three complementary parts:
     - Structure: hexagonal architecture (Cockburn, "Hexagonal architecture", 2005). The core defines ports; audio analysis, rendering, file access and the AI provider are adapters outside it.
     - Behavior: the core implements a feedback loop following the MAPE-K reference model for self-adaptive systems (Kephart and Chess, "The Vision of Autonomic Computing", IEEE Computer 36(1), 2003): measure (Monitor) → diagnose (Analyze) → decide (Plan) → admit and render (Execute) → verify, then accept or roll back, over a run history (Knowledge). Compared with plain MAPE-K, Plan is split into an AI proposal and a deterministic admission step, and Execute is followed by explicit verification with rollback.
     - Implementation discipline: functional core, imperative shell. Stage rules are pure functions over immutable records; side effects happen only in adapters and drivers.
  2. Rings and packages: `core` (`records`, `ports`, `admission`, `verification`, `loop`, and `diagnosis` from its roadmap phase on, ADR-006), `adapters` (`dsp_analysis`, `rendering`, `decision_agent`, `baselines`), `drivers` (`cli`, `experiments`) and `evaluation`. `core.records` defines every core-facing business and port record (including the requests and responses the ports exchange, budgets, run and attempt records, admission results, criteria and verification results), grouped in modules named after the stage or port they serve, together with the cross-record invariant checks that records call in `__post_init__`. Its modules form an acyclic import graph; a record used by several modules (for example the budget records) gets its own module instead of relying on import order. Adapter-local implementation data (for example `VerifiedAudio` with its sample array, `AllocatedWorkspace`, `WrittenWav`, resource limits) stays inside its adapter and is not core vocabulary. `core.ports`, the stage packages and `core.loop` hold behavior only (protocols, response checks, rules, transitions, enforcement, `run()`), so no record ever depends on a port, stage or the loop, and a history record can contain exactly what a port received. There is no per-concept split across layers. Measurement and decision have no core package: measuring and deciding happen in adapters. Their ports (protocols and response checks) are in `core.ports`; the request and response types those ports exchange are defined in `core.records`.
  3. Ports: `AudioAnalyzer`, `DecisionMaker` and `Renderer`, defined in `core.ports` together with the checks on their responses; the request and response types they exchange are records (point 2). The loop calls adapters; adapters never call the loop. No event bus, messaging, plugin mechanism or configurable stage pipeline: the stage order is the method and is fixed in code.
  4. Import rules, enforced by one boundary test: (a) `core` imports nothing outside `core`; (b) `core.records` imports nothing outside itself; `core.ports` imports only `core.records`; stage packages import only `core.records` and `core.ports`; only `core.loop` composes stages and ports; (c) adapters import only `core.records`, `core.ports`, third-party libraries and their own internals; (d) only `drivers.experiments` imports `evaluation`. Rule (d) is necessary but not sufficient for SR-10: an import test is not a filesystem sandbox, and an adapter could still open hidden data by path. SR-10's own requirements stay in force: runtime inputs, decision inputs and runtime configuration contain no hidden-data fields or references, and adapters read only from explicitly supplied roots (ADR-023). SR-10's acceptance tests do not exist yet; they remain required in addition to rule (d).
  5. Immutability (core records; adapter-local data follows its adapter's needs and may hold arrays): core records are `frozen=True` dataclasses validated in `__post_init__` (`slots=True` is the target, added in a separate optional step with its own compatibility tests), with only immutable field types; audio samples never enter records; new versions are made with `dataclasses.replace`; stage outcomes are union types handled with `match` and `assert_never`; mutation stays local to a function or inside adapters. No functional-programming libraries.
  6. Vocabulary with one meaning per term: validation (well-formedness), verification (runtime accept or roll back), evaluation (post-run comparison with hidden ground truth); measurement versus diagnosis; proposal versus admitted action; rendering; integrity check for WAV-file-to-record checks.
  7. "Agent": ADR-005 stays in force. In code, "agent" names only the decision component (`adapters.decision_agent`); the deterministic orchestration is the "control loop". The thesis proposal defines the agent more broadly as LLM, observations, state, tools, constraints and feedback loop together. This conflict is resolved for code naming only: thesis text may use the proposal's broader definition if it states that the AI component is `decision_agent` and the orchestration is deterministic (ADR-004).
  8. Migration, in separate commits with the full test suite passing after each, following [`adr-027-migration-plan.md`](../architecture/adr-027-migration-plan.md). Steps are classified, not all called behavior-preserving: (a) moves that preserve operational behavior (records, ports, stage rules and loop behavior into `core`; infrastructure into `adapters.rendering`; M0 `audio` into `adapters.dsp_analysis`; the CLI into `drivers`); (b) deliberate import-path breaks (compatibility facades and shims deleted); (c) vocabulary renames; (d) `slots=True`. Only (a) and (b) are prerequisites for the control loop; (c) and (d) are optional and may follow later. Old architecture tests are updated in the same commit as each move, and a guarantee ledger maps every old architectural assertion to its replacement test or records why it is dropped. A pilot of the first step decides whether the rest proceeds. Only then is the control loop built in `core.loop`, with test stand-ins for the three ports; contracts it shows to be unnecessary are removed in that work, not during the move. Each step records its evidence in the research log.
- Source: owner discussion with Claude Code on 2026-11-03 (architecture review of `src/`, comparison with the thesis proposal's "How the Autonomous Agent Works" loop, immutability discussion). Codex and Claude Code read the resulting conventions through `CLAUDE.md`.
- Rationale:
  - In the current layout one concept is split across three layers (for example decision records in `domain.decision`, request/response, port and checks in `application.decision`, a future adapter in `infrastructure`), so each change touches several packages, their boundary tests and often an ADR. No component composes the stages, so the system cannot be read end to end; its connections exist only in docstrings referring to a future execution service.
  - The boundaries that matter for the thesis are few: the hidden-reference boundary (SR-10, ADR-010), "the AI proposes, deterministic code admits, renders and verifies" (ADR-004, FR-07) and offline, provider-independent determinism (QR-02, QR-07). The four import rules express exactly these; the previous component matrices enforced more structure than these guarantees need.
  - A visible loop maps directly to FR-06 (decision inputs and outcomes), FR-07 (admission), FR-09 (verification) and FR-12 (per-run record), and lets comparison conditions be swapped as `DecisionMaker` implementations behind one port.
  - Immutable records keep stage rules testable with plain values (QR-02) and remove one source of error: a state or request cannot change after it was used. They are a precondition, not a guarantee. Rollback still requires the retained artifacts to exist and pass integrity checks, the last accepted reference state to be selected correctly and uncertain execution outcomes to be handled. A run history records what the decision component saw only if the actual request and raw response are captured and persisted with provenance (FR-12, QR-03). All 89 existing dataclasses are already frozen, so this formalizes existing practice.
- Consequences:
  - Supersedes, on acceptance: ADR-017 and ADR-022 (component package organization, dependency matrices and compatibility facades). Refines: ADR-011 (domain records become `core.records`, still dependency-free), ADR-013 (validation criteria and results become verification records), ADR-016 and ADR-020 (ports move to `core.ports`; execution contracts are split between `core.admission` and the `Renderer` port), ADR-022 point 5 and ADR-023 to ADR-026 (infrastructure components become internals of `adapters.rendering`). Field semantics recorded in ADR-011 to ADR-026 are unchanged unless a later ADR changes them. File paths in earlier ADRs refer to the layout of their time (index README).
  - About 25 test files need import changes. The ADR-017/ADR-022 boundary and compatibility tests are retired step by step as their modules move, each assertion accounted for in the guarantee ledger; a green behavior-test count alone is not evidence of equal architecture coverage. Compatibility of old import paths is deliberately not kept; this is an API break approved by the owner, not a mechanical change.
  - Effort estimates in the migration plan are provisional until the pilot step has been measured.
  - `docs/architecture/overview.md` describes the target in its "Target pipeline" section now and its implemented components only as each migration step lands.
  - No type checker is added; record immutability is enforced by a test, and `match` exhaustiveness relies on `assert_never` at runtime.
  - No behavior, requirement status or research claim changes with this ADR.
  - Open: whether `core.records` stays one package as it grows; whether `Situation` replaces `DecisionRequest` or wraps it; where run records are persisted (a storage adapter is not decided); whether a type checker should be added later for exhaustiveness checks.
