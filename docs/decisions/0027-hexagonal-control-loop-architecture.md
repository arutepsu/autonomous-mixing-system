# ADR-027 — hexagonal architecture around a MAPE-K control loop, with immutable records (2026-11-03)
- Status: Proposed; awaiting owner review. No code has been moved yet.
- Decision: reorganize the system from horizontal domain/application/infrastructure layers into a hexagonal (ports-and-adapters) modular monolith whose core is the mixing control loop. The binding rules for contributors are kept in [`engineering-conventions.md`](../project/engineering-conventions.md); this ADR records the decision and its reasons.
  1. Architectural style, three complementary parts:
     - Structure: hexagonal architecture (Cockburn, "Hexagonal architecture", 2005). The core defines ports; audio analysis, rendering, file access and the AI provider are adapters outside it.
     - Behavior: the core implements a feedback loop following the MAPE-K reference model for self-adaptive systems (Kephart and Chess, "The Vision of Autonomic Computing", IEEE Computer 36(1), 2003): measure (Monitor) → diagnose (Analyze) → decide (Plan) → admit and render (Execute) → verify, then accept or roll back, over a run history (Knowledge). Compared with plain MAPE-K, Plan is split into an AI proposal and a deterministic admission step, and Execute is followed by explicit verification with rollback.
     - Implementation discipline: functional core, imperative shell. Stage rules are pure functions over immutable records; side effects happen only in adapters and drivers.
  2. Rings and packages: `core` (`records`, `ports`, `measurement`, `diagnosis`, `decision`, `admission`, `verification`, `loop`), `adapters` (`dsp_analysis`, `rendering`, `decision_agent`, `baselines`), `drivers` (`cli`, `experiments`) and `evaluation`. One stage is one package; there is no per-concept split across layers. `core.diagnosis` is created only in its roadmap phase (ADR-006).
  3. Ports: `AudioAnalyzer`, `DecisionMaker` and `Renderer`, defined in `core.ports`. The loop calls adapters; adapters never call the loop. No event bus, messaging, plugin mechanism or configurable stage pipeline: the stage order is the method and is fixed in code.
  4. Import rules, enforced by one boundary test: (a) `core` imports nothing outside `core`; (b) stage packages import only `core.records`, and only `core.loop` composes stages and ports; (c) adapters import only `core.records`, `core.ports`, third-party libraries and their own internals; (d) only `drivers.experiments` imports `evaluation`.
  5. Immutability: records are `frozen=True, slots=True` dataclasses validated in `__post_init__`, with only immutable field types; audio samples never enter records; new versions are made with `dataclasses.replace`; stage outcomes are union types handled with `match` and `assert_never`; mutation stays local to a function or inside adapters. No functional-programming libraries.
  6. Vocabulary with one meaning per term: validation (well-formedness), verification (runtime accept or roll back), evaluation (post-run comparison with hidden ground truth); measurement versus diagnosis; proposal versus admitted action; rendering; integrity check for WAV-file-to-record checks.
  7. "Agent": ADR-005 stays in force. In code, "agent" names only the decision component (`adapters.decision_agent`); the deterministic orchestration is the "control loop". The thesis proposal defines the agent more broadly as LLM, observations, state, tools, constraints and feedback loop together. This conflict is resolved for code naming only: thesis text may use the proposal's broader definition if it states that the AI component is `decision_agent` and the orchestration is deterministic (ADR-004).
  8. Migration, in separate commits with the full test suite passing after each: (a) write `core.loop` against the existing records, with test stand-ins for the three ports, to find which existing contracts are actually needed; (b) move records and pure rules into `core` packages, removing contracts the loop does not need; (c) move infrastructure into `adapters.rendering` and M0 `audio` into `adapters.dsp_analysis`, and the CLI into `drivers`; (d) delete the compatibility facades and shims, update test imports and replace the ADR-017/ADR-022 boundary tests with the single boundary test. Each step names the requirements it serves and its evidence in the research log.
- Source: owner discussion with Claude Code on 2026-11-03 (architecture review of `src/`, comparison with the thesis proposal's "How the Autonomous Agent Works" loop, immutability discussion). Codex and Claude Code read the resulting conventions through `CLAUDE.md`.
- Rationale:
  - In the current layout one concept is split across three layers (for example decision records in `domain.decision`, request/response, port and checks in `application.decision`, a future adapter in `infrastructure`), so each change touches several packages, their boundary tests and often an ADR. No component composes the stages, so the system cannot be read end to end; its connections exist only in docstrings referring to a future execution service.
  - The boundaries that matter for the thesis are few: the hidden-reference boundary (SR-10, ADR-010), "the AI proposes, deterministic code admits, renders and verifies" (ADR-004, FR-07) and offline, provider-independent determinism (QR-02, QR-07). The four import rules express exactly these; the previous component matrices enforced more structure than these guarantees need.
  - A visible loop maps directly to FR-06 (decision inputs and outcomes), FR-07 (admission), FR-09 (verification) and FR-12 (per-run record), and lets comparison conditions be swapped as `DecisionMaker` implementations behind one port.
  - Immutable records make rollback a matter of keeping the previous state, make the run history an exact record of what the decision component saw (FR-12, QR-03, SR-10) and keep stage rules testable with plain values (QR-02). All 89 existing dataclasses are already frozen, so this formalizes existing practice.
- Consequences:
  - Supersedes, on acceptance: ADR-017 and ADR-022 (component package organization, dependency matrices and compatibility facades). Refines: ADR-011 (domain records become `core.records`, still dependency-free), ADR-013 (validation criteria and results become verification records), ADR-016 and ADR-020 (ports move to `core.ports`; execution contracts are split between `core.admission` and the `Renderer` port), ADR-022 point 5 and ADR-023 to ADR-026 (infrastructure components become internals of `adapters.rendering`). Field semantics recorded in ADR-011 to ADR-026 are unchanged unless a later ADR changes them. File paths in earlier ADRs refer to the layout of their time (index README).
  - About 25 test files need import changes. The ADR-017/ADR-022 boundary and compatibility tests are replaced, not migrated. Compatibility of old import paths is deliberately not kept.
  - `docs/architecture/overview.md` describes the target in its "Target pipeline" section now and its implemented components only as each migration step lands.
  - No type checker is added; record immutability is enforced by a test, and `match` exhaustiveness relies on `assert_never` at runtime.
  - No behavior, requirement status or research claim changes with this ADR.
  - Open: whether `core.records` stays one package as it grows; whether `Situation` replaces `DecisionRequest` or wraps it; where run records are persisted (a storage adapter is not decided); whether a type checker should be added later for exhaustiveness checks.
