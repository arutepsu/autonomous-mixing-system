# R5C — Operator configuration and CLI activation for the programmatic DAW agent runtime

> For implementers: tests first. Implement only an individually approved increment (C1–C4 below). Leave changes uncommitted for review. Make no automatic commits, live provider calls, FL Studio operations, script installations or audio changes.

**Status:** Proposed. Planning only, 2026-11-24. Nothing in this document authorizes implementation or live trials.

**Parent plan:** [R5 agent composition](2026-11-23-r5-agent-composition.md), sections 6–7. R5B is implemented and uncommitted (`drivers/agent_runtime.py`, [ADR-042](../../decisions/0042-programmatic-daw-agent-composition.md), Proposed).

**Goal:** Make `daw start` and `daw continue` usable through the existing `DawAgentRuntime`, with:
- one small, versioned, allowlisted run-configuration file;
- a first-session fader confirmation based on a fresh inspection;
- precise manual export instructions;
- unchanged `status` and `recover` guarantees.

There is no second loop, no adapter framework and no decision-file substitute.

**Example file:** [2026-11-24-r5c-run-config-example.json](2026-11-24-r5c-run-config-example.json). It was generated by encoding the existing R5B unit-test fixture records with the real codec, in memory, without writing audio. It illustrates the schema shape only:
- its content hashes are placeholders;
- its criteria values (−12.8 dBFS target, 0.5 dB improvement, 5 dB guard) are test-fixture engineering values, **not recommended thresholds or defaults**.

## 4. Run-configuration schema v1

### 4.1 Principles

- **Two files.** `--config` stays the existing tool configuration (stores, FL journal, profile reference, MIDI, roots, read limits). `--run-config` is new and is read **only by `start`**.
  - Roots come only from the tool configuration. The run file cannot add one.
- **Envelope.** It is plain JSON, with every key allowlisted at every level. Unknown or missing keys are refused with their key path.
- **Codec values.** Every complex value is an existing `core.records` record in the exact codec format, decoded through constructors. After decoding, the driver checks that the value has the expected type; a codec value of another type is refused by key path.
- **Derived fields cannot be declared.** A field the driver derives has no envelope key, so supplying it is an "unknown key" error. The derived fields are:
  1. the analysis specification, which embeds the prepared digest;
  2. the diagnosis measurement definitions and metric IDs;
  3. the DAW control profile;
  4. the provider binding;
  5. the read limits;
  6. the output root key, equal to `daw_session.export_root_key`;
  7. `qualification = UNCALIBRATED`;
  8. the preparation state and roots, which equal the run's `initial_state` and `root_bindings`.

  This removes the circular reference to a digest that does not yet exist (§5).
- **No defaults.** Every criterion, threshold, budget and retry is explicit. The driver adds no musical target, does not derive acceptance thresholds from diagnosis thresholds, and has no fallback for any omitted value.
- **No secrets.** The file has no credential field. `DawAgentBinding.__post_init__` already refuses credential-like keys in the frozen local settings.
- **Evaluation inputs are refused.** Unknown keys are refused anyway, and the codec cannot name anything outside `core.records`. As a named, tested refusal, any key at any envelope level matching `reference`, `hidden`, `evaluation`, `ground_truth`, `clean`, `target_mix` or `injected` is refused with the message "evaluation/hidden inputs are not runtime configuration". Free text in `context` is public provider-visible content. It is not sanitized, and this is documented.

## 5. From declared configuration to the typed request factory

### 5.0 Strict, bounded JSON reading (review correction 3, 2026-11-24)

`_read_strict_json(path, *, max_bytes, max_depth, max_int_digits)` is a private helper in `daw_runtime.py`. It uses only the standard library `json` module and its hooks, so no new dependency is added. Every refusal raises `ConfigError` before any directory, store, journal or transport is created. The CLI maps that to exit 2.

| Hazard | Rule |
| --- | --- |
| Oversized file | The helper requires a regular file (checked with `lstat`; links and reparse points are refused). It opens the file and reads at most `max_bytes + 1` bytes; more than `max_bytes` is refused. It never reads the whole file first. |
| Encoding | The bytes must be strict UTF-8. A byte-order mark is refused, because silently accepting it would mean two spellings of one file. |
| Excessive nesting | Before `json.loads`, a linear scan counts `{` and `[` outside string literals, honouring escapes. Depth above `max_depth` is refused. `RecursionError` is also caught and mapped, as defence in depth. The bound also protects the recursive codec `decode` that runs afterwards. |
| Duplicate keys | `object_pairs_hook` refuses any repeated key in any object, naming the key. The last value never silently wins. |
| Non-finite numbers | `parse_constant` refuses `NaN`, `Infinity` and `-Infinity`. `parse_float` refuses any literal whose `float` value is not finite, such as `1e400`. |
| Large integers | `parse_int` refuses literals with more than `max_int_digits` digits *before* calling `int`. This avoids Python's 4300-digit `ValueError` path and big-integer cost. Range checks stay with the record constructors. |
| Booleans as numbers | Unchanged. Record constructors already check `type(x) is int` and similar. A C1 test pins that `true` is refused for an integer field. |

The bounds are resource limits, not scientific thresholds. They are driver constants with tests:
- `MAX_RUN_CONFIG_BYTES = 4 MiB`, about 100 times the 37 KB example;
- `MAX_RUN_CONFIG_DEPTH = 64`. The example's deepest nesting is 14, measured on 2026-11-24, so this leaves headroom for larger states. C1 asserts the example's actual depth against it.
- `MAX_INT_DIGITS = 20`, which covers 64-bit values.

The helper applies to the run file. Whether the existing tool-configuration loader should adopt it is Q8. Today that loader accepts duplicate keys (last wins), so adopting the helper could refuse files it accepts now. That would change existing behaviour, so it needs separate approval.

### 5.1 Load (pure; no writes, no devices)

`load_run_config(path, tool)` runs these steps:

1. Read and parse the file with the strict, bounded reader in §5.0.
2. Check the envelope's allowlist and the evaluation-name refusal.
3. Decode each codec value and check its type.
4. Build `ClaudeConfig(**provider)`.
5. Check that the experimental policy equals the reviewed policy exactly (D4).
6. Check that every definition analyzer is `LEVEL_ANALYZER` (D3), that definition names are unique, and that each `measurements[].definition` names a declared definition.
7. Check the root keys and `export_root_key` against `tool.roots`.
8. Build `MaskingPreparationRequest(state=initial_state, root_bindings=root_bindings, profile, jobs, UNCALIBRATED, tool.max_file_bytes, tool.max_decoded_bytes, max_elapsed_seconds, experimental_policy)`.

Every failure is a `ConfigError` naming the key path.

### 5.2 Provisional validation (pure, plus read-only baseline reads)

`DawRunConfig.provisional_request(run_id, tool)` builds a complete `RunRequest` with a **provisional** analysis specification, `VersionRef("autonomous_mixing.daw_agent_analysis", "1+unprepared")`:
- in every declared definition;
- in `AnalysisSpec(provisional, declared metric IDs)`.

It has no diagnosis definitions and no provider binding. Constructing it runs every existing structural invariant before anything is written: state/criteria/measurement completeness, recipe/bindings, DAW session against state, and analysis jobs.

`DawAgentRuntime.check(tool, provisional, preparation)` then runs the existing `_preflight` rules: calibrated profile identity, export root, analyzers, native baseline metadata and the header/encoding integrity of the current baseline files. To do so, `_preflight` is changed to take the P1 profile from `preparation.profile` instead of the provider binding. C1 first adds a test that `preparation.profile` equals `plan.prepared.profile`; this equality was not verified during planning. `create` keeps calling `_preflight` after preparation, unchanged in effect.

The provisional request is discarded. It is never recorded and its specification never appears in a store.

### 5.3 Prepared factory (inside `create`)

`DawRunConfig.request_factory(run_id, tool)` returns a closure `factory(plan, diagnostics)` that:

1. sets `spec = plan.specification`, which is bound to the real prepared digest by `create`;
2. builds each declared definition as `MeasurementDefinition(selector, unit, spec, analyzer, alignment, sources)`;
3. computes `metric_ids` as the ordered unique list of the declared definitions' metrics followed by the diagnosis metrics;
4. returns `RunRequest(run_id, initial_state, RunConfiguration(scope, AnalysisSpec(spec, metric_ids), render_spec, context, criteria, controller, budget_limits), policy, renderer_capabilities, processing_spec, recipe, stem_bindings, mix_artifact_id, measurements, (*declared_definitions, *diagnostics), alignment, root_bindings, daw_session.export_root_key, retry_policy, DawSessionConfig(…, profile=calibrated_profile(reference=tool.profile_reference), …))`, with no provider binding.

`create`'s existing checks still apply after the factory returns:
- same run ID and start state;
- no incoming binding;
- exact specification;
- the diagnosis definitions are present.

The factory copies nothing from diagnosis thresholds into the criteria. The diagnosis definitions are *jobs*, not conditions.

## 6. `daw start`

```
autonomous-mixing daw start --config TOOL.json --run-config RUN.json --run-id ID
                            [--accept-current-fader NORMALIZED DB]
```

`--run-id` becomes required (D6). The credential comes from the `ANTHROPIC_API_KEY` environment variable (D7).

### 6.1 Order, side effects and exit codes

| Step | Action | Side effects | On failure |
| --- | --- | --- | --- |
| S0 | Parse arguments; validate the run ID syntax. | none | 2 |
| S1 | `load_config(TOOL)` | read | 2 |
| S2 | `load_run_config(RUN, tool)` (§5.1) | read | 2 |
| S3 | Credential present and nonblank. Never printed or stored. | none | 2 |
| S4 | `<id>.sqlite` or `<id>.runtime` exists. | stat | 4 (`RuntimeRefusal`: "never overwrite; choose a new run ID") |
| S5 | `provisional_request` and `DawAgentRuntime.check` (§5.2). | read baseline WAV headers and bytes | 2 |
| S6 | DAW pre-check (§6.2): open the FL journal writable (exclusive), read the control state and latest anchor, perform **one fresh inspection**, then close. | FL journal: one inspect-ID claim; MIDI inspect only, no write | 4 |
| S7 | `DawAgentRuntime.create(...)`: prepare, run the preflight, assemble the stores and transports. Other `ValueError` → 2, printing "runtime artifacts retained at …; a new run ID is required" (ADR-042: no reuse or deletion). |
| S8 | `with interrupt_cancels(clock): runtime.start()` → existing `run_daw` (start check, initial verification, …) | recorded run; provider dispatch and a fader write are possible | 0 for any `RunReport` or `RunSuspended` (§8). Nothing is dispatched to the provider before S8. No fader write happens before the admitted action inside S8. When S0–S6 fail, the run store and runtime directory do not exist; the tests assert this.

S6 versus S7 race: between closing the FL journal in S6 and S7 reopening it, another process could act. This is accepted and is not a new hazard, for two reasons. The authoritative start check in `run_daw` re-reads the journal under ownership. The execute path's fresh inspection still compares the live fader against the confirmed one before any write.

### 6.2 DAW pre-check and first-session confirmation (D5)

These definitions apply:
- `declared` is `initial_state.daw.track(binding.track_id).confirmed_fader`;
- `fresh` is the S6 inspection's reading;
- `exact(a, b)` compares both `normalized` and `db` with `==` and equal sign bits, the same comparison `daw_start_check` uses.

The rules, in order:

1. **FL journal busy or unreadable:** 4.
2. **Unresolved commands:** 4, naming the command IDs and "resolve with `daw recover` first".
3. **Blocked conversion:** 4.
4. **Latest event cannot be anchored:** 4.
5. **Fresh inspection fails,** meaning not `ok`, a timeout, an unsupported device, or identity that is not exactly the binding's build/project title/insert index/insert name: 4. Nothing is created.
6. **Journal has an anchor:**
   - `--accept-current-fader` given: refused with 2 ("only for a journal without an anchor"). The flag can never override history.
   - Otherwise both `exact(declared, anchor.reading)` and `exact(fresh, anchor.reading)` are required. A failure gives 4: "the DAW differs from its journaled state (unexplained)".
7. **Journal has no anchor** (first session):
   - **Without the flag:** print `fresh` exactly, as Python `repr` for both coordinates, and exit 4. Print: "first session: no journaled fader state. If this is the intended starting state, re-run with `--accept-current-fader <normalized> <db>`". No store is created.
   - **With the flag:** both `exact(flag, fresh)` and `exact(declared, fresh)` are required. This is a fresh inspection *in this invocation*, not the one printed earlier. A failure gives 4 and shows all three readings.

The confirmation is an operator declaration that the live reading equals the declared initial state. It is not stored as an FL anchor, and the declared state is never rewritten (P3).

## 7. `daw continue`

```
autonomous-mixing daw continue --config TOOL.json --run-id ID --export-id EXPORT_ID
                               --operator NAME --attestation TEXT
```

`--export-id` and `--operator` are new and required (D8). There is no `--run-config`, so passing one is an argparse error (2). The stored request is the only source of run settings.

| Step | Action | On failure |
| --- | --- | --- |
| C0 | Parse arguments; check that the run ID, export ID, operator and attestation are nonblank. | 2 |
| C1 | `load_config(TOOL)`; credential present. | 2 |
| C2 | `<id>.sqlite` and `<id>.runtime` exist. | 4 |
| C3 | `DawAgentRuntime.reopen(config, run_id, api_key, provider_config=None)`, which: | 4 |
| | – opens the store exclusively (busy gives 4, "continuation in progress"; a schema 1 legacy store gives 4); | |
| | – reconstructs `ClaudeConfig` from the recorded identity; | |

| | – loads the frozen manifest; | |
| | – verifies the evidence; | |

| | – opens the FL journal (busy gives 4). | |
| C4 | `--export-id` must equal the suspension's `awaiting.request.export_id`. | 4, showing the awaiting ID. Nothing is hashed. |
| C5 | Build the manifest through `FileExportHandoff.attestation_digests(awaiting)` (§7.1): every workspace and file-safety check runs before any output file is opened. | C7 | `runtime.close()` in `finally` | — |

**What may change between start and continue:**
- **May change:** the credential value (not part of any identity); the operator, attestation and export ID (per continuation); the clock and identities (fresh).
- **May not change:** anything else, including provider settings, prompt/schema, policy/plan, run settings, tool-configuration paths, MIDI ports, timeout, roots and limits. A change is refused (4) before any import, provider call or write.

**Duplicate protection** keeps the existing rules:
- A repeated identical continue after acceptance reaches `reopen` as `FINISHED` or as a *different* suspension. `--export-id` then fails at C4, or `admit_continuation` refuses with `ALREADY_CONTINUED`.
- A concurrent continue is busy at C3.

Import stays authoritative for stray files, links, encoding and hash changes after C5.

### 7.1 Safe manifest digests (review correction 2, 2026-11-24)

Hashing reads the operator's files before the importer runs. The importer's later checks therefore cannot undo a read that has already followed a link, a reparse point or a replaced workspace out of the workspace. The manifest builder must apply the same file-safety rules **before opening any output file**.

To keep one implementation of those rules, C3 adds one public method to the existing adapter: `FileExportHandoff.attestation_digests(awaiting) -> tuple[DawExportedFile, ...] | DawImportRejected`. It belongs in the export-handoff adapter because it has the same responsibility: verifying files in a prepared workspace. It is not added to the `DawExportHandoff` port. The driver calls it on the runtime's concrete `export_handoff`. The order reuses the existing private checks unchanged:

1. **`_context`:** the awaiting request must belong to a current checkpoint of this run; otherwise `REQUEST_MISMATCH`.
2. **`_check_workspace`:**
   - re-validate the allocation under the configured root;
   - `lstat` the directory: it must be a plain directory, not a link or reparse point;
   - its identity must equal `awaiting.directory_identity` (otherwise `WORKSPACE_REPLACED`).
3. **`_check_request_file`:** the prepared request file must exist, unlinked, with its recorded identity and exact bytes.
4. **`_check_listing`:** the workspace must hold exactly the request file plus the declared output names. Stray entries, case or normalization collisions, and missing outputs are refused.
5. **`_check_objects`:** for each declared output:
   - it is a regular file, not a link or reparse point, with no other hard link;
   - no two names are the same physical file;
   - the name resolves directly inside the workspace.
6. **Hash each declared output in order:**
   - `os.open` with `O_RDONLY | O_BINARY`, plus `O_NOFOLLOW` where the platform has it;
   - `fstat` identity must equal the identity recorded by step 5;
   - read in chunks up to `max_file_bytes + 1` bytes; a larger file is refused;
   - compute the SHA-256.
7. **Re-check observed metadata.** For every file and the directory, `_observed(lstat)` must be unchanged since step 5. Otherwise `WORKSPACE_CHANGED`.

Everything happens inside the configured export root. No glob or recursive listing is used, and nothing outside `workspace_directory` is opened. Import repeats its own full verification (format and encoding, integrity hash, continuity) independently. A file swapped between C5 and C6 fails import as a hash mismatch or `WORKSPACE_CHANGED`. That failure is recorded as the run's existing `EXPORT_IMPORT_REJECTED` path.

**Residual risk:** each check is followed by a later use. Like the existing importer, the method is not race-free against a hostile local process. It shrinks the window and refuses any change it observes, and makes no stronger claim.

## 8. Operator output and exit codes

Exit codes keep 0/2/4 (D9):

| Code | Meaning |
| --- | --- |
| 0 | The command ran: it produced and printed a recorded `RunSuspended` or `RunReport`, whatever the run outcome. |
| 2 | Invalid arguments or configuration (including every §5.0 parsing refusal), or no credential. Nothing was created before S7. An S7 failure is the only case with retained runtime artifacts, and the message names them. |
| 4 | Refused or stopped. The message states which of the two cases below applies. |

Exit 4 has two cases, and the message must say which one applies (review correction 1):
- **Refused before effects:** any failure in S4–S6, C2–C5, or a `DawContinuationRefused`. The message is `REFUSED: … (no provider call or fader write was made by this command)`. That clause is printed only in this case; the tests pin it to these steps. S6's inspect-ID claim in the FL journal is mentioned if it occurred.
- **Stopped after effects were possible:** an exception inside S8 or C6. The message is `STOPPED: <exception type>: run <id> may have dispatched a decision, written the fader or recorded an acceptance; its recorded state is uncertain. Inspect with 'daw status'; use 'daw recover' if it reports an interruption.` The driver does not claim what happened. If the run store can still be read in-process, it prints the last recorded usage and authoritative reference, labelled "last recorded".

The printed outcome is separate from the exit code. The first line is always one of the keywords below, followed by `run <id>`. The keyword names the **termination**, not the history of the run. A run can accept a candidate and later abstain or reach a limit; it can also write, be rejected and recover. So no keyword implies that nothing was written or accepted.

| Result | First line | Then |
| --- | --- | --- |
| `RunSuspended` | `SUSPENDED: awaiting your manual export` | The export instructions (below). |
| `RunReport`, `CANDIDATE_CRITERIA_MET` | `ACCEPTED: the latest candidate met the declared criteria` | "Engineering criteria only, not a quality judgement." |
| `RunReport`, `INITIAL_CRITERIA_MET` | `NO CHANGE NEEDED: the initial state already met the declared criteria` | — |
| `RunReport`, outcome `ABSTAINED` | `ABSTAINED: <termination reason>` | The explanation: the run ended without a further admissible change. Earlier writes, rollbacks or acceptances are shown in the block below. |
| `RunReport`, outcome `LIMIT_REACHED` | `LIMIT REACHED: <reason>` | — |
| `RunReport`, outcome `CANCELLED` | `CANCELLED: <reason>` | — |
| `RunReport`, outcome `FAILED` | `FAILED: <reason>` | — |
| `DawContinuationRefused` | `REFUSED: <code>` (exit 4) | The explanation. |
| Pre-run refusal | `REFUSED: <explanation>` (exit 4) | — |

**Recorded-state block.** It is printed after every `RunReport` and `RunSuspended`. Every value is read from the report or trace; none is inferred:
- **Usage against limits:** decision calls, attempts, recovery operations, elapsed seconds and **DAW writes** (`BudgetUsage.daw_writes` against `max_daw_writes`).
- **Acceptances:** the number of committed acceptances in the trace.
- **Authoritative state:** `authoritative` (revision and sequence), or `unknown` when it is `None`.
- **Verified state:** `verified` (revision), or `not verified` when it is `None`.
- **Final project state:** `final_run.final_project_state`, verbatim (for example `unknown`).
- **Uncertainty:**
  - the terminal append is not `TraceAppended` ("the terminal record may not be durable");
  - `unacknowledged_events` is not empty (their count);
  - the termination reason is `ACCEPTANCE_COMMIT_UNCERTAIN`, `RESTORATION_UNCERTAIN` or `ACCEPTED_STATE_INTEGRITY_UNCERTAIN`;
  - the final project state is `UNKNOWN`.

  In any of these cases, print "uncertain: inspect with 'daw status'; use 'daw recover' if it reports an interruption".
- **For a suspension:** the write that awaits export (normalized and dB, exactly) and the accepted reference it rests on.

**Manual export instructions.** They are built only from the saved `DawCorrectionSuspended` checkpoint: `awaiting` and `write`. They contain:

1. **Project:** the binding's project title, insert index and name. **Leave the fader where the run set it.** The written reading is shown exactly (normalized and dB).
2. **Format:** the export format container and subtype; sample rate; start seconds; frame count and the resulting duration; render specification.
3. **Destination:** `workspace_directory`, verbatim. Do not delete `export-request.json`, and add no other files.
4. **Files to export,** one line each: `file_name`, kind, source tracks, channel count, and the artifact it replaces.
5. **Saving and exporting are manual.** The system never saves or exports.
6. **The exact next command:**
   `autonomous-mixing daw continue --config <TOOL> --run-id <id> --export-id <export_id> --operator <NAME> --attestation "<what you exported>"`.

**Credential hygiene.** The credential never appears in stdout, stderr, stores, evidence or audit files. Exceptions raised while the transport is constructed are reported by type and a fixed message, never with their text, because transport redaction was not verified during this planning. C2 adds a sentinel test.

## 9. `status` and `recover`

**`status`** stays read-only: no lock, no MIDI, no network. For provider-bound runs, C4 makes a purely additive change (D10):
- **Classification:** stays `provider_evidence_unavailable`, with the same exit 4, so it never claims resumability.
- **Explanation:** becomes "provider-run provenance is not verified by `status`; `daw continue` verifies it under ownership before any effect".
- **New field `provider`,** from the stored `DawAgentBinding` only: provider, API version, requested model, parameters, prompt and response-schema references, diagnosis method, prepared digest, and the SHA-256 of `runtime_settings`. Paths are not echoed.
- **New field `recorded_state`:** the result of `classify_run` over the run store and the **read-only** FL facts, using the existing refusing transport factory. It is labelled `unverified`. When it is a suspension, `awaiting_export` is shown exactly as for non-provider runs.
- **The decision-exchange store and evidence files are not opened.** A read-only verification mode is open question Q2.

**`recover`** is unchanged. Provider-bound runs use the same journal-only views and operations, with no provider transport. C4 adds a regression proving that `recover` on an interrupted provider-bound run neither constructs a provider transport nor reads the audit store, and that its options equal those of an otherwise identical non-provider run.

### C2.1 Command line

```
autonomous-mixing daw start --config TOOL.json --run-config RUN.json --run-id ID
                            [--accept-current-fader NORMALIZED DB]
```

- **`--run-config` and `--run-id`** are required (D6). The run ID is validated with the existing `DawToolConfig.store_path` rule.
- **`--accept-current-fader`** takes exactly two values, each of which must match the plain decimal pattern `-?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][-+]?[0-9]+)?`. Each is parsed with `float` and must be finite. The pattern refuses `nan`, `inf`, hexadecimal, `1_0` and whitespace, all of which `float()` would otherwise accept. Because `-0.0` is preserved, the sign of zero participates in the comparison. Any refusal exits 2.

An absent or blank value exits 2: "no provider credential: set ANTHROPIC_API_KEY (it is never stored or printed)". The value is passed as an argument only and never appears in a message, store or file.

### C2 review fix — unreleased pre-check transport (2026-11-24, uncommitted)

**Finding (reproduced by the reviewer).** The FL controller records a failed transport close only in memory: it blocks its own further operations and retains the transport. `daw_precheck` could still return a successful inspection. `start` then created a fresh runtime controller without that block. With a simulated transport whose first close fails, the command returned 0/SUSPENDED after one provider call, two inspections and one gain write.

**Fix (tests first):**
- **Adapter:** `FlStudioParameterController.blocked`, a public read-only property over the existing in-memory block. No behaviour change.
- **Pre-check:** `daw_precheck` checks it immediately after the inspection, before evaluating the result, because a failed inspection can also leave a transport held. If it is set:
  - the pre-check controller is kept in `daw_commands._UNRELEASED_CONTROLLERS` for the process lifetime, so the unreleased transport and the block stay owned and are never closed again or replaced;
  - it raises `RuntimeRefusal` (exit 4, "could not release"). Runtime creation never begins.

**Regressions:**
- **Close fails after a successful inspection:** no provider construction or call, one MIDI transport opened and closed once, exactly one inspection, no gain write, no run store, and the controller retained with the transport.
- **Close fails after a timed-out inspection:** the refusal names the release failure, not only the timeout.

RED first: exit 0/SUSPENDED reproduced the finding, and the second test showed only the timeout refusal.

**Limit:** the block is process-local, because the controller does not persist it in the FL journal. A new process starts with a fresh controller, and the operator is told to check the MIDI connection first. Persisting the block would be an adapter/journal design change outside C2.

### C3.1 Command line

```
autonomous-mixing daw continue --config TOOL.json --run-id ID --export-id EXPORT_ID
                               --operator NAME --attestation TEXT
```

- All five options are required. There is no `--run-config` and no provider option, so supplying one is an argparse error (exit 2).
- `--operator` and `--attestation` must be nonblank. `--operator` must satisfy `VersionRef.name`, and `--attestation` must satisfy `require_text`. The CLI checks these before opening anything (exit 2).
- `attested_by = VersionRef(operator, "daw-cli-attestation-1")` (D8).
- The credential comes only from `ANTHROPIC_API_KEY`, read after the tool configuration validates (exit 2 if absent or blank). It is never stored or printed.

### C3.4 `FileExportHandoff.attestation_digests` (the one narrow method)

The order reuses the importer's private checks unchanged; the importer keeps its own full verification:

1. `context = self._context(awaiting.request)`. `None` → `DawImportRejected(REQUEST_MISMATCH, "no configured state has the request's before checkpoint")`.
2. `directory = self._check_workspace(awaiting, context)`: allocation under the configured root, a plain directory (not a link or reparse point), identity equal to `awaiting.directory_identity`.
3. `self._check_request_file(awaiting, directory / DAW_EXPORT_REQUEST_FILE)`: unlinked, single hard link, prepared identity, exact bytes and fingerprint.
4. `self._check_listing(awaiting.request, directory)`: exactly the request file plus the declared output names; no stray, colliding or missing entries.
5. `statuses = self._check_objects(awaiting, directory)`: regular files, no link or reparse point, `st_nlink == 1`, distinct physical files, each resolving directly inside the workspace.
6. For each declared output in order:
   - `os.open(directory / file_name, O_RDONLY | O_BINARY | O_NOFOLLOW-if-available)`;
   - `fstat` identity must equal that output's `statuses[i]` identity (otherwise `WORKSPACE_CHANGED`);
   - read in chunks of `_READ_CHUNK` up to `self._limits.max_file_bytes + 1` bytes; a larger file is the existing `RESOURCE_LIMIT` code;
   - compute the SHA-256 and close the descriptor in `finally`.
7. Re-`lstat` every output and the request file. `_observed` must be unchanged, and the directory identity must be unchanged (otherwise `WORKSPACE_CHANGED`).
8. Return `DawExportedFile(artifact_id, file_name, sha256)` per output. `_Rejected` maps to `DawImportRejected` exactly as `import_files` does, and an `OSError` maps to `UNAVAILABLE`.

The method never globs, never opens a name outside the declared set, and never writes. Hashing is **not** import: K8's importer re-verifies everything. A file changed between K6 and K8 is still rejected there, which ends the run with a recorded outcome (F6), exit 0 with `FAILED: export_import_rejected`. The method is not race-free against a hostile local process (§7.1 residual risk).

### C3.6 Resources and cleanup (process-local MIDI block across commands)

- **K2** makes `continue` honour a block retained by an earlier `start` or `continue` in the same process.
- **`_retain_if_blocked(controller)`** appends a runtime controller that is `blocked` after K8 (or after C2's S8) to `_UNRELEASED_CONTROLLERS` before `runtime.close()`. Later `start`/`continue` calls in the process then refuse. It holds the controller and its retained transports for the process lifetime: no retry, reset or persistence.
  - **This closes gap F9 for `start` as well.** Changing `start` is a C2 behaviour change, so it needs approval (D-C3-4).
- **Ownership on each failure:**
  - **K4:** `reopen` closes everything it opened, which is existing behaviour.
  - **K5–K9:** the command owns `runtime` and closes it in `finally`, after `_retain_if_blocked`.
  - **Hashing:** descriptors are closed in `finally` inside the adapter.
  - **Import, dispatch and output:** these happen inside `continue_export`, whose resources belong to the runtime.
  - **Output formatting** is pure and runs after `close`. A printing failure cannot change a recorded outcome or turn it into a refusal.
- **Exception reporting:** messages are printed only for this driver's own `ConfigError` and `RuntimeRefusal` (internal texts) and for `DawImportRejected`/`DawContinuationRefused` explanations, which are internal records. Everything else is reported by type only. Credential sentinel tests cover construction (K4), dispatch (K8) and cleanup (K9).

### C3.7 Factual output (reuses C2 `describe_outcome`)

- **First lines:**
  - `ACCEPTED`;
  - `NO CHANGE NEEDED`, which is not expected after a continuation but is handled;
  - `ABSTAINED` / `LIMIT REACHED` / `CANCELLED` / `FAILED`;
  - `SUSPENDED` with new export instructions;
  - `REFUSED: <code>`.
- **The recorded-state block** comes from the records. After an accepted intermediate candidate followed by abstention or a limit, it shows `DAW writes ≥ 1/…`, `acceptances: 1` and the accepted authoritative revision. The keyword names only the termination.
- **The "next" line in suspension instructions** becomes:
  `next, after exporting: autonomous-mixing daw continue --config "…" --run-id … --export-id … --operator <NAME> --attestation "<what you exported>"`.
  The "R5C C3 … not available" wording is removed (F10), and the C2 test that pins it is updated.
- **Exit codes:**
  - **0:** any recorded report or suspension, including `FAILED: export_import_rejected`;
  - **2:** input;
  - **4:** refusals, cleanup failure and `STOPPED`.
